# Object API quick reference

The whole HTTP surface of the Notees server, for scripts and agents. The CLI wraps the same routes ([cli.md](cli.md)); the web app's feature pages describe what the routes are for.

Base URL `http://localhost:8377`, auth header `X-API-Key: nk_…` on every call except the public probes (`/healthz`, `/api/version`, `/api/meta`, `/api/openapi.json`, `/api/server-info`, `/api/setup`, `/api/auth/login`, `/api/auth/signup` — the last only exists while `NOTEES_SIGNUP_ENABLED` is on). Bodies are camelCase JSON; `contentAst` follows the [SCHEMA.md grammar](../packages/protocol/SCHEMA.md).

**The developer contract is machine-readable:** `GET /api/openapi.json` serves the OpenAPI 3.1 document of the whole HTTP surface, and CI fails when it drifts from the registered routes. It pins the error taxonomy (`x-error-codes` — every failure answers `{"error": {code, message, status}}`, codes and statuses are stable), the rate limits (`x-rate-limits` — 10k req/min/IP global fallback, 30k envelopes/min/workspace relay batches, 10 logins/min/IP + the 5-failures lockout), the API-key scope vocabulary (`x-api-key-scopes`), and the revision/idempotency rules below.

Clients read their local derived stores; content changes ride the relay log.)* |

| `GET /api/resolve?doi=` · `?isbn=` · `?arxiv=` · `?pmid=` · `?ads=` | Resolve source metadata from an identifier — exactly one required (400 otherwise). Crossref (DOI), OpenLibrary (ISBN), arXiv (id), PubMed esummary (PMID), ADS Solr (bibcode); answers the unified record `{classKey, title, authors[], editors[], fields{}, doi?, isbn?, pmid?, url?, year?, publisher?}`. When the record carries a DOI, an Unpaywall lookup adds `pdf: {url}`, the open-access PDF link when one exists — its failure never fails the resolve. The server's only outbound metadata egress — only the identifier leaves, never workspace content; the one exception is YOUR ADS API token riding the `Authorization` header to ADS alone — the `?ads=` branch requires a user principal (the operator key gets 401) and a configured token (422 otherwise, set it in Settings → Account). Plan-07 prefs are ONE opaque blob: keyless (unwrapped) blobs are read server-side as before; WRAPPED (keyed) blobs are opaque, so the web client passes the unwrapped credential explicitly via the `x-ads-api-token` request header. The `sources` settings can hard-off the egress (`resolverEnabled: false` → 403 `resolver_disabled`, default ON); provider failure/timeout → 502 `resolver_unavailable`; unknown identifier → 404. Cached 24 h |

| `POST /api/shares` · `GET /api/shares?nodeId=` · `DELETE /api/shares/:token` · `PUT /api/shares/:token/artifact` | Read-only public page shares: mint an unguessable token (`{nodeId, expiresAt?}` → `{share: {token, urlPath, …}}`), list (owner/admin), revoke (immediate). | `GET /api/operations?workspaceId=&afterSeq=&limit=` | Paginated read of the workspace's relay operation log — the audit feed for agents (cursor shape like relay catch-up; entries are envelope-v3 ops) |

**Agent safety.** Mutating JSON routes honor `Idempotency-Key: <key>`: the first 2xx response is replayed verbatim (header `x-idempotency-replay: true`) for an identical retry within 24h — no second write enters the log; reusing a key with a *different* request fails 409 `idempotency_replay`. Multipart uploads are excluded (CAS dedupes identical bytes by hash). The relay `/batch` needs nothing: it dedupes by envelope id.

**Scoped API keys (server side).** `POST /api/api-keys` accepts an optional `scopes` list (e.g. `["objects.read"]` for a read-only agent); keys without scopes — and the operator key and sessions — stay unrestricted. Scope checks are per-route (the OpenAPI `x-required-scope` extension is the enforcement table): an out-of-scope call gets 403 `scope_denied`, and scoped keys are rejected on the whole relay surface. The reserved `admin` scope gained its first enforcement with the plugin registry: `/api/plugins*` accepts the operator key or an administrator account, and a scoped key additionally needs `admin`. The in-app Read/Write/Admin checkboxes are separate web work.

**Operator key on the account plane.** Account routes are user-bound (session or per-user key), with one deliberate carve-out: the account-**discovery** reads `GET /api/auth/me` and `GET /api/workspaces` also accept the operator key — the deployment owner, whose data-plane access is already unrestricted, needs the workspace directory to point machines (and the web client's API-key sign-in tab) at where to sync. `GET /api/auth/me` answers as a synthetic owner identity (`{id: "operator", email: "operator", isAdmin: true}`) and `GET /api/workspaces` returns the whole directory — every workspace row plus any id present only in the relay log (imported/migrated workspaces), each tagged `role: "operator"` and carrying a per-workspace `encrypted` flag (a `workspace_key` row exists). Everything mutating stays user-bound: profile, prefs, key minting, and workspace create/rename still reject the operator key with 401.

One curl, end to end:

```bash
curl -s -X POST localhost:8377/api/relay/v2/batch \
  -H "X-API-Key: $NOTEES_API_KEY" -H 'Content-Type: application/json' \
  -d '{"envelopes":[{"id":"<uuidv7>","protocolVersion":3,"workspaceId":"<ws>",
       "actorId":"<user>","deviceId":"curl","hlc":{"physical":<ms>,"logical":0},
       "affectedNodeIds":["<node>"],"opType":"object.create",
       "timestamp":"<iso>","payload":{"objectId":"<node>","isEmbedded":false,
       "contentAst":[{"type":"text","text":"Back via curl"}]}}]}'
```

The relay surface your clients sync through (`POST /api/relay/v2/batch`, `POST /catch-up`, snapshot endpoints, `/stats`, `/ws/:workspaceId`) is specified in [packages/protocol/WIRE.md](../packages/protocol/WIRE.md). You rarely touch it directly — the `packages/sync` engine and the web `WorkspaceClient` speak it for you. Request bodies are capped at 128 MiB app-wide, with one deliberate exception: the client-produced snapshot upload (`PUT /api/relay/v2/snapshot/data`) rides a route-local **512 MiB** cap — a big workspace's full local projection is the largest body this API carries. Past the single-body comfort threshold the reference client compacts and chunks instead of skipping: the buffered image is VACUUMed first (replay-derived free pages don't ride along), sealed, and — when still large — uploaded as ordered parts (`PUT /api/relay/v2/snapshot/data/part`, ≤64 MiB each) committed by `POST /api/relay/v2/snapshot/data/commit`, which reassembles the bytes and runs the same sanity gate. Only a failure in that flow (or a body past the 512 MiB route cap) surfaces to the client, reported once per session instead of silently retried (the server-side snapshot, built by the relay itself, keeps covering restore). Both `/snapshot/data` directions negotiate **gzip Content-Encoding** (transfer only — no wire change): the GET gzips the blob when the client's `Accept-Encoding` advertises it (browsers do automatically and decompress transparently; identity otherwise, so clients that parse the body themselves are unaffected), and a PUT carrying `Content-Encoding: gzip` is transparently decompressed before every sanity gate and the store — invalid gzip is rejected 400 with nothing stored. The web client gzips its uploads via the built-in `CompressionStream`, so the caps bound the **compressed** size.

**Snapshot images: clone & import.** Both workspace-rebuild surfaces move a serialized `@notees/store` database (the derived projection), not log history. `POST /api/workspaces/:id/clone` snapshots a source workspace's derived store (consistent online backup) into a fresh workspace; `PUT /api/relay/v2/snapshot/data?…&mode=import` installs an image file into an existing workspace (`scripts/import-snapshot.mjs` is the ready-made driver). The target must be **envelope-empty** — refused with 409 otherwise — and the image must carry node rows at any log size (422). **Checkpoint semantics:** an imported or cloned workspace's log starts from its seed envelopes — the history is not in the log, and the installed snapshot is load-bearing: a derived-cache wipe rehydrates from the snapshot plus the log, not the log alone.

Workflow rules are managed through this API only (no UI yet): `GET/POST /api/workflows`, `GET/PATCH/DELETE /api/workflows/:id`, and the run audit at `GET /api/workflows/:id/runs` — see [features/workflows.md](features/workflows.md) for the vocabulary and an example, and [developers/workflows.md](developers/workflows.md) for the table shapes, the loop policy, and the audit semantics.
