# Plugins

**Workspace Settings → Plugins** — the plugin registry (owner/admin only — the **Admin settings** entry in the account popup): installed manifests list with their declared capabilities (export formats, importers, commands, widgets) and an enable toggle, plus an "Install manifest" paste-JSON box validated against the manifest grammar before anything is stored.

The registry is honest scaffolding — the plugin *runtime* that would execute a manifest is not built yet, so installing stores validated data and an enable flag, nothing more. The registry's HTTP surface enforces the reserved `admin` API-key scope ([api.md](../api.md)); why core flows never depend on plugins is [philosophy.md](../philosophy.md)'s ("What we took — and the wounds that became our rules").

One piece of the runtime's infrastructure already exists as a shipped service because a first consumer needed it: the **shared external-reference mapping** (`external_ref` — workspace + integration + the source's own identifier → node, with first/last-seen bookkeeping). Every connection-style integration answers the same three questions with it — idempotent re-import (resolve before writing, so a re-sync updates instead of duplicating), provenance (which integration owns a node), and last-seen bookkeeping (the honest base for vanished-from-source handling, never automatic deletion). The one-way calendar subscriptions ([calendar.md](calendar.md#subscribed-calendars-one-way-ical)) are the first consumer (`calendar:<feed-url>` namespaces); read-it-later providers, highlight importers, and contacts importers reuse the same table when they land, and the plugin runtime will expose it as a service instead of every plugin reinventing it.
