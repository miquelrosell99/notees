# Calendar and day pages

A date is a node, not a string (SCHEMA.md "Dates"), and the day page is the date's home in the UI. Two surfaces render it — the Calendar's day view (a dedicated aggregation surface) and the day page itself (an ordinary page, so it also appears in the journal feed, search, and everywhere else pages do) — and both read the *same* materialized state, never a bespoke query. This page covers both surfaces, quick capture, and the date model; the tasks that surface on days are [tasks.md](tasks.md)'s; the date property's picker is [properties.md](properties.md)'s.

## The Calendar

The sidebar's **Calendar** entry (hide it from Workspace Settings → Sidebar Visibility) opens a day view for one date — today by default:

- **Day header** — the weekday, a Today marker when you're on today, the full date in your date-format setting, the ISO week number, and ‹ / › buttons to step one day either side (Today jumps back).
- **Quick create** — one chip per class that has a date property (the system Event, Meeting and Birthday classes are the examples — their date property is set to the selected day). Clicking a chip creates an object of that class with that date set to the selected day and opens it. By default every eligible class appears — on a fresh workspace those are the system Task, Event, Meeting and Birthday classes (the click sets a task's Scheduled, or an event/meeting/birthday's date). To narrow the list, use **Workspace Settings → Calendar Quick-Create** (the workspace switcher's gear): uncheck the classes you don't want. The choice is stored per workspace on this device; "Reset to defaults" returns to the automatic list. The bar's **repeat picker** (the ⟳ control) stamps the new object's date with a recurrence — pick Weekly and every chip click that day creates a weekly series anchored on the selected day.
- **Daily note** — the selected day's page embedded inline as an **editable outline**: its child blocks render through the shared collection outline (edit titles and text where they render, drag to reorder, the trailing "+ Add block" row appends at the end) — no page header, the top bar already names the day. No page yet? The "+ Daily Note" button creates it in place.
- **Repeating events** — an event (or task) whose date carries a **repeat** rule shows on every occurrence day: the Dated and Tasks sections list it (one row per series — occurrences are computed, not stored, so there are no copies to clean up), and the month grid dots every occurrence day. Editing the event edits the whole series. Set or change the rule from the event's **Properties** panel (the ⟳ picker on the date pill — re-picking the date keeps the rule), from the calendar's quick-create bar, or clear it back to "Does not repeat". The picker offers None / Daily / Weekly / Weekdays (Mon–Fri) / Monthly / Yearly. A repeating task appears in Scheduled on each occurrence day and never goes Overdue — the series rolls forward instead. **Completing one occurrence completes only that day**: the occurrence-done toggle (the tasks hub's checkbox on the day context, the task's own surfaces) records the date (the occurrence renders struck-through, every other day stays open, reopening removes just that date) — the tasks hub's checkbox, off the day context, still means the whole task (the checkbox semantics are [tasks.md](tasks.md)'s).
- **Daily note** — the selected day's page embedded inline (edit it where it renders; an embedded feed entry skips the page chrome per the embedded-feed rulings). No page yet? The "+ Daily Note" button creates it in place.
- **Tasks** — open tasks scheduled for the day as plain **editable outline rows** (the shared collection grammar — inline title/text editing, drag to reorder; no checkbox, status pill, or repeat marker, owner 2026-10-23), with overdue ones grouped above under their own heading. "New" creates a task scheduled for the selected day. A task appears here when its **Scheduled** property points at this day; Done and Cancelled tasks never list.
- **Dated** — everything else that references this day through a date property (a meeting held that day, a range ending on it), plain editable outline rows riding the **breadcrumb trail** above each row (its containing-page ancestry — the collection default).
- **Created** — objects created on the selected day, newest first, plain editable outline rows with breadcrumbs, same as Dated. Main objects only — blocks created that day are inline scaffolding, not listed.
- **Month grid** (right column) — the selected month with today highlighted, days that have a note dotted, and prev/next arrows; click any day to select it. The **month and year title are clickable buttons** exactly like the calendar popup's (the month prominent, the year greyed — clicking opens the monthly/yearly date-chain pages); the Days/Months/Years switch zooms the grid (jumping back to today rides the top bar's Today button). A day some object **references** through a date property (a meeting held that day, a range end) is dotted too — not just days that already have a note. Calendar breadth rides the edge index: date refs and range ends fan out to the deterministic day node at projection time, so "objects dated this day" is one materialized backlink read — the month grid's range-aware dots (a day with dated objects but no note still shows) and the week agenda both derive from it, per the same exclusion rules as the Dated section. (Qualified-link metadata ranges edge from their start day only — the middle days stay undotted, the honest visibility of the current model.) Under the grid, the **agenda** lists the selected week's dated objects **as collection groups** — one collapsible group per day with plain editable outline rows (breadcrumbs on), the day header click selecting that day.
- **Reviewed days** — a day page carries a **Reviewed** boolean property (set it from the day page's Properties). Reviewed is a property, not a protocol: a plain boolean schema bound to the `day` class (self-healed at a fixed id, `hideWhenEmpty` so the panel stays quiet), written from the day page's Properties, read by the calendar grids as a small tint — a skim shows which daily notes you already went over. The flag is an ordinary boolean property — it syncs like everything else.

Filter tabs (All / Daily note / Tasks / Dated / Created) narrow the left column to one section.

## Day pages

A day page is an ordinary page (the journal is the feed of them), and it carries its own chrome:

- **The date header** — the weekday and a Today flag ride a small line above the title; the title itself is the date in your date-format setting, with the day's **ISO week number** as a small flag after it. (The old ‹ / Today / › stepping bar is gone — step days from the calendar popup or the top-bar calendar; the **Reviewed** checkbox lived on that bar and is set from the page's Properties now.)
- **Three sections**, below the page's own content and collapsed like every system section — hidden entirely when there's nothing to show: **Tasks** (open tasks scheduled for this day, overdue above, with the same done checkbox as the Tasks hub), **Dated** (everything else that references the day), and **Created** (objects created that day — main objects only, blocks are inline scaffolding and never listed — newest first, cards by default with an outline switch). **Month and year pages carry the same Created section** — everything created inside that month/year. The day-page branch is read-model only: a node whose id parses at day precision gets the date header and, below its own content, Tasks / Dated / Created — the open-task partition (the tasks hub's exact write on the checkbox), the day node's existing backlink set minus date-chain sources and tasks, and a `createdAt` range query (main nodes only). All three honor the system-sections lazy contract ([links.md](links.md)) — collapsed by default, nothing loads until the expand, hidden entirely when empty (the Created count is the one structured query, gated the same way unlinked mentions gates itself). Embedded renders (the journal feed, the calendar's daily-note embed) skip both: they already sit on aggregation surfaces.

**Ctrl/Cmd+Shift+T** (or the sidebar's **Today** row) opens today's page from anywhere in the app. Note the browser reservation: Ctrl+Shift+T is "reopen closed tab" in most browsers, so the open-today chord fires only where the browser yields it (and as Cmd+Shift+T on macOS). The command palette answers the date affordances — `is_daily:` prefix, Date Pages section, formatted keywords ([search.md](search.md)) — and the CLI verbs are `notees today` / `notees journal`.

## The date model

- **Recurrence is computed, not stored.** A repeating event is one node whose date value carries a small RRULE-lite rule (`daily`, `weekly`, `weekdays`, `monthly`, `yearly` — additive value metadata, SCHEMA.md "Recurrence"; no op, no wire change). Occurrences are virtual: the day view lists the event on every occurrence day (one row per series — never phantom rows), the month grid dots each occurrence, and editing the event edits the series. The rule is authored from the calendar's quick-create bar or the Properties panel's date pill, and a date re-pick keeps it. A repeating task schedules on occurrence days and is never overdue — missed days roll forward to the next occurrence. **Completing an occurrence completes that day, not the series**: the occurrence-done toggle (the tasks hub's checkbox on the day context, the task's own surfaces) records the date in the value's metadata (`completedOccurrences`), the occurrence renders struck-through on its day while every other occurrence stays open, and reopening removes just that date — no nodes are materialized, and the toggle off the occurrence context (the tasks hub) still means "the whole task". Not shipped: the unreviewed-days queue.
- **Events are the calendar's base class; meetings and birthdays are events.** The seeded `event` class is the calendar family root — its single date property (whole-day per the dates law, no clock times) makes it quick-create eligible through the same date-binding rule as tasks. `meeting` extends `event` with a meeting-specific family (its own date plus text location/agenda); `birthday` extends `event` the other way — person-typed: a birthday links TO a person (`birthdayPerson`), the date still rides the event chain, and a person's page lists their birthdays through the ordinary backlinks section. Both are ordinary classed pages — queryable, template-able, mentionable; a date dots the month grid and lists the object in the day's Dated section like any dated object. The system `event`/`meeting`/`birthday` classes are plain seeds; existing workspaces materialize the families through the same idempotent ensure as the task family, and the calendar chips pick all three classes up through the generic date-binding rule.
- **Local midnight is the only "today".** Every today path (the shortcut, the calendar, the journal, the default-view landing) derives the day from local midnight; the UTC `.slice` pattern is banned by design.

## Quick capture

**Ctrl/Cmd+Shift+N** quick-adds to today's page or the Inbox from anywhere; at narrow widths a floating **+ button** opens the same quick-add modal ([pages.md](pages.md#narrow-screens)).
