# Classes

A class is a node: addressable, linkable, annotatable, in the same table as the things it classifies — and *for* configuration: property bindings, inheritance, templates. This page covers the class view, creating classes, and the workspace feature toggles; why classes-as-nodes is the law is [philosophy.md](../philosophy.md#classes-are-nodes); class chips and the `+` class picker are [links.md](links.md); the classed-nodes table and cards ride the collection rulings in [views.md](views.md).

## The class view

A node marked as a class (always a root) gets the **page view itself** — same chrome, same editable bullet-tree body (classes are containers and can hold child blocks) — plus class-relevant sections. The class page renders the **panelled layout**: the first column hosts the **Properties** panel + the **property definitions** list (one row per binding — drag to reorder; the row click opens the property's base-definition modal where the schema-level default + render contracts live; the class-level inline editor is gone) + the **templates** cards (bound instantiation templates — see [templates.md](templates.md)), while the content column keeps the **classed nodes** table (the members — one column per property definition, table by default, outline/cards switchable; cards renders the **board** when a bound select property can group — one column per option, drag a card between columns to set its value; the class page's centerpiece, the Capacities/Tana lesson: instances are the page; the section header's **Add member** action and the empty state create a node classed with the class — visible even when the class has no members yet). The app top bar's **layout button** flips the current node between the sidebar layout and the in-flow **sections** layout (Properties + property definitions + templates stacked in the content flow, the extends pills pinned to the card's top-left corner) — session-only, never stored; the icon names the active mode. The **extends** pills (the class's extensions, added with "＋ Add class extension" from a class-only selector; × removes an extension; cycles fail loud) ride the nodeview top bar in the panelled layout, the card's top-left corner in the sections layout. The class page carries the **context column** too (graph/TOC/Activity/Comments are node-relevant for every node kind, class pages included; the column is [pages.md](pages.md#page-chrome--what-sticks-and-where)'s). The class's color and curated icon live in the header (one dot opens the picker; the swatch strip is gone). Below the body, the standard system sections plus **Extended by** (the extenders as a tree of direct extends edges — a subclass nests under its own direct parent, never as a top-level row under an ancestor; a backlink-class read). There is no separate description shelf: title-is-content means the class's title IS its description.

Class nodes are always roots by construction — `is_class` implies no parent, enforced by a schema CHECK and a fail-loud move-guard; the one tree rule left is that a class can never be a child. Classes may themselves have non-class children. Inheritance is data: `extends` is an m2m node-typed property between class nodes — multiple inheritance from the start, diamonds natural, cycles rejected fail-loud — and effective membership is own classes ∪ ancestors, with a deterministic binding-resolution order (own binding → shortest extends-path → earliest-authored) ([philosophy.md](../philosophy.md#classes-are-nodes)).

## Creating classes

The **Classes** hub's **New class** button (or the command palette's **New class…**) opens the creation dialog: a blank class (name, icon, color), or **Deploy system class** — the seeded system classes this workspace doesn't have yet (Person, Meeting, Source, the source family, …). Deploying authors the class at its designed identity, its place in the hierarchy, and its property family in one idempotent step — the same shape a server-seeded workspace starts with, so everything downstream (quick-create, calendar chips, citation fields) just works. Declaration-first is the standing rule: create classes, configure them, use them later or never ([pages.md](pages.md#promotion-and-demotion)).

From the CLI and API, declaring a class is `notees object create --isClass` (a `class.create` op under the hood) — see [cli.md](../cli.md) and [api.md](../api.md).

## Workspace Settings → Features

The core class families as per-workspace toggles: Tasks, Events, Meetings, Sources, Persons. A family off hides its classes from pickers, search, and hubs (family changes cascade — Events off hides Meetings and Birthdays too) while existing objects keep their data and stay in the graph. Turning a family **off** with existing instances asks first — the confirmation states that the objects keep their data and the family's surfaces hide (Cancel changes nothing); an empty family (or any enable) switches immediately.
