# Queries

Saved, live queries over the workspace: query blocks sitting in a page's content, saved views filed as tabs, and the structured-filters panel that sections and views share. The query language itself (endpoints, QueryAst shape) is [api.md](../api.md)'s; the chrome the filters ride (tab bar, sort button, windows) is [views.md](views.md)'s; the query runtime's contracts (lazy loading, counts) are [links.md](links.md)'s for the system sections.

## Query blocks & saved views

A **query block** (insert one with `/query`) is a live saved query sitting in a page's content — and a normal block besides: you type on the row like any other block (its text is just text, a title for the query). The block's `query` content token renders nothing inside the row; it marks the block and carries the **default** tab's AST, so the query syncs like any content. Below the content row the block renders the nodecollection chrome — the same tabs-and-buttons surface the system sections carry ([views.md](views.md#hosted-tab-bar-chrome)): a **Default** tab (the token's query) plus custom tabs, the quick search + the toggleable **structured-filters panel** (the full-grammar builder, not a separate one), a transient list/table switch, and the results. **Applying** the builder's draft rewrites the *selected* tab's query — the Default tab commits through the content update path (the token's AST, synced like any edit); a custom tab commits to the node's stored view. **+** creates a tab immediately from the bar's draft (no modal); the view (list/table) switch is transient surface state — nothing about it is stored. The results are a projection, not a snapshot — the block re-runs when the store changes (notification bursts coalesce — a burst costs at most one extra run, never one per envelope), the 200-row cap is a render window with an honest load-more ([views.md](views.md#long-lists--one-pagination-convention)), and **Export** downloads the current results as one Markdown file. An empty query — workspace scope, no conditions, no aggregation — renders nothing, never the whole graph: until you set a filter it answers "Set a query to see results."; a scope-only query (this page / pages) is a deliberate choice and still runs.

The hub's **New query** modal keeps the compact builder (scope, class, the bits, text-contains, a created window, one sort, a group-by with a measure) for ad-hoc composing and editing saved views — and it still **asks before it overwrites**: if a query was hand-written with constructs the builder can't represent (OR/NOT groups, property conditions, multi-sort), the modal shows a read-only summary of what it can represent and asks before anything is overwritten (an explicit "edit anyway" opt-in). On the block itself there is no such gate — the builder is the full grammar, nothing is lossy.

The created-window fields accept relative placeholders alongside fixed dates: **`{today}`, `{this_week}`, `{this_month}`, `{this_year}`** — resolved when the query runs, so "created after {today}" means today, every day. Date fields accept `{today}`-style placeholders that resolve at run time, so "this week" means the week it is read, on any device, in any timezone.

The account popup's **Queries** entry (it left the nav sidebar, query blocks carry the saved-query surface in context) is the workspace's saved-views surface — the hub gathers the workspace's saved views as tabs over one ordinary page (created on first save — its content *is* the views, so opening the page shows them as query blocks). **New query** opens the same builder as a modal: **Run** executes it ad hoc (nothing persists; ad-hoc runs are session-only until named), **Save as view** names it and files it as a tab. Tabs are the page's saved views — rename, duplicate, reorder (move left/right), set the **default** (the view the section opens on; the default is a flag in the record, not a hardcoded choice), or delete from the tab's ⋯ menu. Saved views are ordinary query tokens hosted on a normal "Queries" page (linked at the bottom of the hub) — they sync like any content, render as query blocks when you open that page, and can be embedded anywhere else a query block can. Everything persists through the content update path — no view entity, no new op, device state stays out of the log.

A query whose result set contains both a node and its descendant shows the descendant twice — nested under its parent and as its own row; that is the honest graph read, not a bug.

## Section filters

The reference sections at a page's bottom (**Backlinks**, **Unlinked mentions**, [links.md](links.md)) and a class page's **Classed nodes** table carry filter chrome: a quick text field (substring over titles, with an **×** inside to clear) plus a **structured-filters panel that is a full block query builder**, v1-style: every block is a row of columns — a **type** select (Class, Type, Placement, Content, Property, Links, Parent, Cover, Banner, Alias, Created, Edited), an **operator** select whose options vary by type (is / is not; contains / does not contain / full-text; equals / not equals / contains / is set / is not set / ordering; after / before; is set / is not set), then the **value** control typed per family (the property-table register — numeric keyboard for number properties, a node picker for node targets, `{today}`-style placeholders for dates). **Class** is hierarchy-aware; **Created**/**Edited** are the create/edit date windows; **Links** and **Parent** carry the v1 **mode switch**: *static* picks a node, *dynamic* nests a whole query that defines the target set — "links to a person node with age greater than 50" builds as Links → dynamic → Class person + Property age > 50. The menu's **All of (AND)** / **Any of (OR)** entries insert a nested group (the group's header toggle flips it later) and **Exclude (NOT)** wraps any condition or group; rows reorder with the chevrons. The top level is not a group — it renders bare. The panel names the match live through the hosted tab bar: the **active tab carries a total-count badge** beside its name (the open tab's displayed row count — replacing the old "N of M nodes match" foot line; the section-header count badge survives as the count's home on sections WITHOUT tabs, refined 2026-10-23 — a section names its count exactly once); both switches — Match ALL/ANY and Blocks/Raw AST — share the panel's top row). Everything evaluates locally except **Links**/**full-text** (and dynamic targets), which ride one query-channel probe per edit. Filtering is transient — one filter per section view, lost on reload — and it narrows rows, never hides the section: an emptying filter reads **0** on the tab badge (and **0 of N** in the bar while the query is active), and **Clear filter** (or removing every condition) restores the rows. Each section owns its own filter — one never leaks across.

The chrome this rides — the hosted tab bar with its +, view switcher, and quick search — is the generic collection chrome, documented once in [views.md](views.md#hosted-tab-bar-chrome). Two escapes from transience live on the panel itself: **Save as tab** persists the composed draft as a new hosted tab (auto-named, selected on save, the transient filter clears — the new tab owns the query), and the builder's **Raw AST** toggle switches the panel to the composed query as JSON — copy it out or paste one in (validated against the query grammar; half-typed rows drop when switching).
