# Views and collections

Every node collection — a hub, a class's members, query results, a page's reference sections — renders through one shared set of rulings: the list view is the outline, the card is the node, the sort button rides everything, long lists window honestly, and the hosted chrome (tab bar, +, quick search) is identical everywhere. The page's own view triad (outline/prose/cards) is [outliner.md](outliner.md)'s and [pages.md](pages.md)'s; the filter builder on top of these views is [queries.md](queries.md)'s.

## The list view is the outline view

The **list** mode of every node collection (the first icon in the view switcher — the Tasks hub, the Pages/Classes hubs, a class's classed-nodes section, query results, the references grouping) renders the **same block row the page body uses** — there is no separate thin row, never a reduced row kind. Every row is the real outline row: bullet, inline content, property icon buttons (a task's **Status** rides its row as the clickable circle — click it to change the value; [properties.md](properties.md#inline-property-buttons)), the classes column, tags, and the collapsed **Properties** section. Above each row rides the **containing-page breadcrumb trail** (owner 2026-10-22 — ancestors only, read-only navigation context; a crumb click opens the node): backlink rows read "where is this", a task shows its page, a hub row its parentage. The trail collapses away on a parentless row, and in the references grouping the containing page's own crumb drops — the group header already names it, the trail shows only the in-page path. The page body (child blocks), the Child pages section, the Classed nodes section, and the Extended-by section opt out (`showBreadcrumbs` — their rows already carry their ancestry). **Children nest under their row**, recursively, with the collapse chevron — a task's notes live under the task. **Rows with children open collapsed** (owner 2026-10-21): every row in a collection list — a page with child blocks, a block with nested content, a backlink source with context — starts folded behind its chevron, so the list reads one row per item; an expansion is session-local display state — the collapsed default re-applies on the next session.

On an **editing surface** (the Tasks hub is one) rows edit **inline**: click a row's text to type in it, the status/priority buttons write on click, the row context menu (right-click the bullet area or the row's text — the same menu) offers the block gestures. On a **read-only surface** the same rows render with every gesture off and the chrome statically shown — the inert twin, the alignment deliberate: **clicking a row's content does nothing** (no hover wash either — the row-hover feedback lives on the bullet alone), and **opening a node rides the bullet element** (click — or shift+click to peek in the sidebar). A query whose result set contains both a node and its descendant shows the descendant twice — nested under its parent and as its own row; that is the honest graph read, not a bug. Block-scale widgets (embeds, queries, whiteboards, assets) inside a list row render their compact placeholder — the live surface belongs to the page body, and a live query inside a result row could recurse.

## The card is the node, not a summary

A cards-mode card reads as ONE surface — the v1 node card, 1:1 (owner 2026-10-13): the cover sits in its cell as a matted card element (horizontal layouts), the row hairlines run the full card width, and the FIRST row is the containing-page breadcrumbs (absent on a parentless node). The title is the page-view title itself — the same title BlockRow, read-only: inline class links and mentions render live; a click opens the node, a **right-click opens the node's context menu** (no "…" button — the selection checkbox is the only hover chrome). Below, every row is its own hairline-separated row: the **classes** row and the **tags** row — the same interactive lists the nodeview bar and page header use, so classes and tags are **addable and removable right on the card** (date nodes stay locked) — then the **properties** section — the nodeview properties table itself (name column | value column, editable like the panel): every bound property rides on every card, unset ones as empty fields with the add affordance — the table's full column set. On a class page the cards' property rows mirror the table's bound columns. Last, the **content row**: a header (collapse chevron + "Content") over the node's child blocks, collapsed by default. Cards resolve a node's children themselves: the collection's tree/"show children" props do not apply to cards (a classed node's blocks show on its card). The **table** mode is the twin ruling: rows are always flat, children never render. The table's **name cell is the node's title block row** (owner 2026-10-21 — the page header's title projection, not a text flatten): inline tokens render read mode — markdown links as links, class chips resolved, never the raw `[label](href)` source — and a **click inside the cell edits inline through the full block editor** (Enter flushes and leaves edit), exactly like the page header's title; **navigation rides the pinned Open button** (click opens, shift+click peeks in the sidebar). The **property cells** edit in place on editable tables (the class page's classed-nodes section is one): booleans toggle, selects drop down, url/email/number commit on Enter/blur (empty unsets), dates open the shared date picker, single node values open the anchored node picker (the Open button still owns navigation), **text cells ARE the value's carrier block rendered through the same title BlockRow** (owner 2026-10-21 — a text cell reads exactly like the name cell: a click edits rich content through the full block editor, the pinned Open button navigates to the carrier's page; an empty cell reads **Empty** — one click creates the carrier and lands in the editor; leaving it emptied unsets the property and the orphaned carrier is trashed), **multi-value node properties wear the pill cluster** (the metadata row's contract, table-scaled — owner 2026-10-21: an empty cell reads **Empty** and one click opens the picker; once values exist, every value a pill tinted with the linked node's color, click opens, hover-reveal × unsets its own slot, "+ Add" appends at the next free idx, the schema's target class filter scopes the search and the create row), and **asset properties wear the asset buttons** (owner 2026-10-21 — an empty cell reads **Empty** and one click opens the picker; once files exist, every value a pill labeled with the file's original name whose click **downloads** the asset, the ❝ **annotations** toggle opens the annotations panel anchored under the cell, × unsets, and the "+ Add" picker's create row IS the upload action: "Upload file…" opens the upload modal and the uploaded file links at the next free idx); other multi-value properties, and every property on a read-only table, render all their values joined. An **empty value cell reads "Empty"** — the muted state placeholder across text, node, date, asset, and scalar cells (owner 2026-10-21, settled same day: a picker cell's accessible name still names the action "Add \<name\>", and the pill clusters' "+ Add \<name\>" pills keep the action label — they are the add affordance itself); a date **never** navigates on a text click — editable value clicks open the picker, readonly values are plain text, and the **Created/Edited stamps are plain text with the pinned day-page Open button** (the retired click-to-navigate day link). The columns ride **fixed-layout widths**: every column has a default share (name 32ch, properties 18ch, the stamps 12ch — character units in the table font) and a **dragged header divider** re-commits its width — the default IS the minimum, a column widens from its default and never narrows below it (session-state; ArrowLeft/Right nudge the focused divider) — content wraps inside its lane and a crowded table scrolls horizontally, spare width lands proportionally on the widest columns. On cards the title and child blocks stay read-only — the outline mode is the editing surface for card content.

## The flat cards flow

The flat cards grid arranges three ways, picked by the **Card layout** toggle in the cards toolbar — the flow parameter: how the flat card set arranges into columns (one enum, not a multi-column × grid pair, since that decomposition creates a meaningless single-column-grid combination):

- **Masonry** (the default): adaptive visual columns; every card keeps its natural height and the columns pack vertically — the recovered original card look.
- **Grid**: the same adaptive columns with row alignment — the cards in each row stretch to the row's height.
- **Single column**: one full-width card per row, a plain stack.

## The cards board (group-by)

**Kanban is not a view mode — it is what cards mode becomes when the collection can group by a select property.** On the Tasks hub and on a class page whose property definitions include a select property with options, the **Cards** mode renders the board: one column per option (plus a trailing **None** for the unset) and the same node cards as the flat grid. **Drag a card onto a column to set that property's value** (drop on None clears it); multi-select properties put a card in every column it carries. Columns collapse via their header chevron, each column windows its cards independently ([long lists](#long-lists--one-pagination-convention)), and the cover-position + selection-export toolbars are the cards toolbars. The board rides no flow toggle — its columns are the groupBy, not a visual layout. Without a usable select property, cards stays the flat grid.

## Covers in card views

The **Assets** hub lists every asset-classed node as cards by default, and its cards default to the **cover top** placement (image assets read as a thumbnail gallery). Every other cards surface defaults to **no cover** until you pick a placement — and the moment you pick one anywhere, that choice becomes the single device-wide cover position: the per-surface rule governs only the default before any choice exists. The cover position is one of the card view's two independent device-wide parameters (no-cover / top / left / right — where a card's cover sits; the old "card layout" naming, which was always cover placement).

Under a cover layout the cover slot renders on **every** card, empty or not (owner 2026-10-13): a card whose node has no cover shows the quiet **Add cover** affordance in the slot — clicking opens the image-only upload modal and the uploaded image becomes the node's cover — so a missing cover is visible and fillable right there. (Asset cards are never "empty": their imagery is their own bytes. The **no cover** layout renders no slot at all — the card stays text-only.) The cover field, the Cover badge, and the header-card cover are [pages.md](pages.md#page-chrome--what-sticks-and-where)'s.

## View modes stick (this device)

The collection view modes persist like the page triad: the view mode of every hub (Tasks, Assets, Pages, …), the classed-nodes mode on a class page, the cards cover position, and the cards flow (single column / grid / masonry) — once chosen, they survive reloads. Storage is device-local (`notees.settings.*`): another device does not see them, and none of it ever enters the operation log. If a saved mode no longer applies (e.g. cards on a surface that no longer offers it), the surface falls back to its default — a persisted mode the surface no longer offers falls back to the surface default instead of resurrecting a dead switch (the retired kanban mode reads back as cards — the board is cards + property groupBy, not a mode of its own). The page's own outline/prose/cards triad follows the same law on its page-specific seam ([pages.md](pages.md#page-chrome--what-sticks-and-where)).

**The condensed layer is not a mode**: it answers a different axis — *how much of each block's own prose shows* — and commutes with the triad (condensed over prose is the Nelson-like flat page of excerpts). It persists per page on the same device-local seam (`condensed.<pageId>`), with the stretched set beside the folds in `notees.stretched.v1.<pageId>`; the view-mode choice and the layer never clear each other. The full layer ruling is [outliner.md](outliner.md)'s.

## The sort button

**Every collection view carries the sort button** (owner 2026-10-13 — the table's mdi-sort control, generalized): the list view's read-only projections (the reference groups, the child-page tree, the Extended-by tree, flat member lists) and the cards grid offer a small **Sort by** panel — list: **Dates first** / **Name A–Z** / **Default order**; cards: **Last edited** (the default, newest first) / **Name A–Z**. **Dates first** (the named mode) orders the *pages*, never the blocks: date pages newest → oldest, then the other pages A–Z — a grouped rendering sorts its groups (the rows inside a group keep their document position), a tree sorts every sibling level, a flat list sorts its items. Defaults: **Backlinks and Unlinked mentions open Dates first; Child pages, Extended by, and Classed nodes open Name A–Z** (the classed-nodes table included — its container default is Name-asc; the tasks/assets hubs' tables open on **Edited, newest first**). The table keeps its per-column sort machinery (the Edited column rides `updatedAt` in the user's date format; containers own table defaults — an unset table renders the container's row order, so query results keep the query's order; a sort survives its column being hidden). The defaults are live: while a section's quick search ranks its pool, the ranked order leads (the search ruling — its ids are membership AND order) and the default yields until a sort is picked explicitly. Editable surfaces (the outliner, the task list) and the cards board hide the button — the drag order is the order there.

## Long lists — one pagination convention

Every list that can grow without a bound windows the same way:

- **A session-local window, grown by an honest affordance.** The first 100 rows render; a **"Show more (N remaining)"** button at the list's end grows the window by another 100. The count names what is hidden — a window never drops data silently, and the button is a real, keyboard-focusable control.
- **Sorting or filtering resets the window.** A resort re-narrows to the first 100 instead of inheriting a grown window.
- **Counts, badges, and exports always read the FULL set.** Hub totals, board column counts, reference-group counts, and every export (the table's CSV whole-view download among them) cover everything — the window is display-only. The table's header checkbox selects exactly what is loaded, and says so: **"Select all loaded rows."**
- **Where it applies:** every node-collection view — outline lists and grouped sections, cards grids and board columns (each column its own window), tables, and read-only page trees (the child-pages projection, the reference sections).
- **Where it deliberately does not:** the **editable outliner tree** — a window could hide the block you just created; the editor's collapse chrome is the existing answer. The **command palette and the pickers** stay bounded-scroll surfaces narrowed by typing: their lists live inside a fixed-height scroller and the keyboard cycles the filtered set, so a Show-more would fight the search idiom.
- **The feeds keep their own honest patterns.** The journal windows around today with scroll sentinels (prepends compensate your scroll position so the viewport stays put), search pages through a cursor ("Load more results"), saved queries window at 200 rows with "N more — load more", and the Activity feed is a bounded summary by design (20 created / 10 edited — a digest, not an archive).

## Custom views as section tabs

Every collection-backed section (a page's backlinks, its unlinked mentions, a class's classed nodes) hosts custom views (owner ruling — cross-device). The collection renders a tab bar — **Default** first (permanent, never closable — it renders the factory behavior) plus custom tabs in order — and a **+** opens the query builder ([queries.md](queries.md)): the composed filter persists verbatim as the view's stored query and refines the section's row set on top of its default query. Per tab: rename, reorder, delete; **Reset to default** removes every custom view of the section (emptying restores factory behavior — the default is derived, never stored). The tab bar stays visible whenever the section renders — a live filter emptying a tab keeps the chrome, with the empty line ("No matching rows.") inside the selected tab's body (the strip itself hides only when the page has no references at all, the system-section hide-when-empty ruling). Views are per-user prefs-channel state (`/api/me/nodes/:nodeId/sections/:sectionKey/views`, the favorites/recents ruling — [feature-status.md](../feature-status.md)); offline they are read-only.

## Hosted tab bar chrome

The filter chrome rides the hosted tab bar's **far right**, one row with the section's tabs (owner 2026-10-12 — the Classed nodes table and the reference sections alike): every button on that row sits right — the add-view **+**, the view switcher, the view's own sort/columns/more (the sort button rides every collection view — [above](#the-sort-button); the reference lists open **Dates first** — date pages newest → oldest, then A–Z — and Child pages / Extended by / Classed nodes open **Name A–Z**) — with the quick text search a **permanent field** between them (on wide viewports; at narrow widths it folds into a magnifier-popup), and the structured-filters toggle opens the builder in a full-width region **below the row: the row's controls stay put** (the builder renders last and wraps beneath, never pushing the buttons down). The add-view + rides the tablist's end beside the tabs; one FilterQuery per section. Each section owns its own filter — one never leaks across.
