- [x] **Deletion/restore semantics** — DONE 2026-10-03: the corners are specced and implemented. Deleting a parent trashes the subtree with it (restore is whole-tree — the corner question resolves to "rides along", not "orphaned to roots"). `object.restore {objectId}` (op-types.ts, catalog entry, canonical `object-restore.json` fixture — gate list 11→12) reactivates exactly the nodes that rode the root's trash event — a descendant carrying its OWN trash row was trashed independently and stays trashed (its subtree rides with it, not with this restore) — and consumes the root's trash row. LWW against `object.delete` is plain log order: the single global relay log applies each op to every replica once, so the pair converges with no merge metadata. Restoring a node whose parent was permanently deleted: the original recommendation (reparent under the nearest parentless-or-main-presenting ancestor, else workspace root) collapses in practice — with the derived schema's enforced `parent_id` FK the dangling state is unrepresentable (reachable only with FK enforcement off, i.e. imported/legacy data), so the applier reparents to the workspace root when the parent row is missing (defensive branch) and otherwise leaves a present-but-inactive parent alone (an active child under a trashed parent is transient; restoring the parent later heals the tree — never data loss). The page-listing fact stands: `WHERE is_class = 0 AND parent_id IS NULL` — class exclusion is structural (`is_class = 1`). API: `POST /api/objects/:id/restore` (the applier's `not_found` surfaces as 404 on permanently deleted nodes); the trash lists via `GET /api/objects?trashed=true`, and `?parent=<uuid>` filters direct children. CLI: `notees object restore <id>…`, `notees object list --trashed|--parent <id>`; the web UI joined the surface 2026-10-14 (the sidebar's **Trash** hub: `client.listTrashed()` reads the `trash` table joined to the inactive node rows, **Restore** emits `object.restore`, **Delete permanently** the confirmed `object.delete {permanent: true}` — no wire change). `trash.empty {}` (op-types.ts, catalog entry, canonical `trash-empty.json` fixture — gate list 26→27; the first `trash.*` op) permanently deletes EVERY node carrying a non-permanent trash row — the bulk "Empty trash" gesture — with the subtree riding each root exactly as `object.delete {permanent: true}`; the applier shares that op's subtree-purge body. The set is evaluated at APPLY time against the trash table, not authored as an id list: the envelope stays small at any trash size, and `object.restore` keeps its plain log-order LWW against the deletes — a restore landing BEFORE the empty takes the node out of the apply-time set (it no longer carries a trash row, so empty does not touch it); one landing after is LWW against the permanent tombstones as usual. Roots are snapshotted and iterated in id order; a root consumed by an earlier iteration (its subtree contained another independently-trashed root) is skipped by the missing-node-row check, and a stale non-permanent trash row with no node row (legacy dangling state) is swept rather than failing replay. Replay is idempotent (an empty trash table no-ops); the payload is the empty strict object — any field is rejected outright. The web Trash hub's **Empty trash** confirms then emits it (2026-10-14). **LOCKSTEP (SHIPPED 2026-10-03, same day):** `notees-gtk` v2.0.0-m4 and `notees-flutter` v2.0.0-m14 both implement `object.restore` with the four-semantics coverage; envelope v3 unchanged.

## Content grammar (NORMATIVE, firmed 2026-09-25)

A block node's content is **one flat, ordered token array** (`contentAst: ContentToken[]`). There are no block-level "segments" — paragraph spacing, quotes, queries, whiteboards, assets, and embeds are all tokens in the same stream. The design law applies: nothing prohibits where a token may appear; rendering defines presentation.

Decisions recorded with the grammar:

- **Fork 2 — marks are attributes** on text runs (`marks: ["bold","italic","strike","highlight","code"]`), not nested nodes. Overlaps (a bold phrase containing a mention, a typed-link word in italics) split runs at boundaries — standard rich-text mechanism; no nesting interaction matrix.
- **Fork 3 — `class_link` ASSERTS membership** (owner ruling 2026-10-15, superseding the 2026-09-25 render-only decision): every `class_link` token in a stored content stream IS a classing of its node. The object.create/update appliers apply the OR-set add for the referenced classes, so ANY writer — web gesture, CLI, GTK, Flutter, imports — converges: an inline reference can never exist without its membership. The inverse is write-time impossible too: `class.unassign` REFUSES while the node's stored content references the class (loud failure, never applied — the removal gesture strips the links first, a content `object.update` + the unassign in envelope order, and the session undo reverts the pair). The web's removal surfaces dissolve the links to plain text (the labels they rendered) with the same gesture. Removing a class — archival (`active = false`) or trash — NEVER sweeps its memberships (owner ruling 2026-10-22, membership rides): `class_member_set` rows are never touched and nodes keep their `class_ids`, so restoring/unarchiving the class brings it back with every assignment intact; stripping a class from nodes stays the explicit per-node `class.unassign`. A PERMANENTLY deleted class's memberships become the dangling-reference state (the content links survive and render pending). View rulings: the node's classes pills hide any class its content references inline (the link IS the marker — never two visible references), and the edge index never extracts the token — no backlinks, no graph edges, no link analytics: it is a class marker with the node-link look, not a node link. One-off wording via optional `displayText`; renames re-resolve everywhere (the wire stores no text).
- **Fork 4 — `mention` stores id only**; display resolves the target's current name at render time (auto-rename free). `text` (captured surface form) is non-authoritative; `displayText` overrides per-link ("the Republic"); broken targets render the raw id (the fallback rule).
- **Line breaks (owner decision, 2026-09-25):** exactly one break token — `hard_break` = shift+enter, a line jump inside a block. **Enter always creates a new node** (a new bullet); there is no paragraph concept within a block and no `paragraph_break` token.
- **Prose mode** (bullets hidden, indents flattened) is a VIEW transform, not content.

## The token view record (NORMATIVE, 2026-10-04)

The `query` token's optional `view` record is the saved view's persisted configuration. The protocol grammar keeps it a **free-form record** (`z.record(z.unknown())` — additive by construction: foreign keys ride along, newer writers must not break older readers, writers merge into the existing record and never replace it). The disciplined shape (web client reader/writer: `apps/web/src/ui/queryViewRecord.ts`):

- `mode: "list" | "table"` — the result rendering (list default; anything unknown reads back as list).
- `title?: string` — the saved view's display name (ViewTabs; absent = the positional "Query N" fallback). A saved view is otherwise anonymous — title-is-content names NODES, not views.
- `isDefault?: boolean` — the section opens on this saved view (the per-surface default is configuration in the record, not code). One token per section carries the flag.

Reserved for future writers (readers must tolerate them; no current writer emits them): `columns`, `sort`, `groupBy`, `pageSize` (the PG9 property-column ride). A version key is intentionally absent — the free-form record IS the versioning mechanism (unknown keys ignore forward-compatibly).

Query blocks are the saved-view vehicle: the token is content, so a saved query rides the op log — synced, local-first, no view entity, no new op. The Queries hub hosts workspace-level saved views as tokens on an ordinary page.

## Query compile-time placeholders (NORMATIVE, 2026-10-04)

The QueryAST carries **explicit ids only** — no editor-relative id placeholders ("this page" is baked at write time by the builder as a `subtree` scope; the once-reserved `currentNodeId` compile option was dead and is removed). `{today}`-style **date placeholders** ARE ordinary strings in two positions, resolved to concrete dates at compile time against the run clock (`@notees/query` `CompileOptions.now`, default the current instant — a saved view re-evaluates on the day it runs):

- `{today}`, `{this_week}` (ISO week, Monday start), `{this_month}`, `{this_year}`;
- `createdAfter`/`createdBefore` timestamps: the placeholder resolves to the period's local-day boundary expressed in UTC (`created_at` is UTC on the wire) — After floors at the local day start, Before ceilings at the local day end (both inclusive, matching the ops);
- property-condition comparison values (`eq`/`neq`/`gt`/`gte`/`lt`/`lte`): the placeholder resolves to the period start as a plain `YYYY-MM-DD` date — the hand-typed shape, so the ISO-date arms (including the date-node-ref containment match) apply. `contains` (text-substring) and unknown `{...}` tokens never resolve — they stay literal.

## Whiteboard modeling (NORMATIVE, 2026-09-26)

- **Cards are child blocks of the whiteboard node** — full grammar (mentions, chips, typed links), backlinks, search indexing, focused view, classing. The whiteboard is a **spatial view of its subtree**: geometry (`x, y, w, h` per card) lives in the layout token **keyed by node id**; the tree holds content, the token holds geometry. The outliner can render the same children as bullets — same nodes, three views (spatial / outline / focused).
- **Shapes (rectangles, circles, connectors, freehand strokes) are layout-token-only** — pure geometry, no identity, no node overhead. The web toolset's shape set (rect/ellipse/line/arrow/text) plus per-shape `color` and `strokeWidth` and per-stroke `color`/`width`/`highlight` ride the same layout JSON: colors follow the data-color grammar (preset token or `#RRGGBB`), widths are world units. Card color is NOT geometry — it is the node color field. Client layout parsers stay migration-tolerant: unknown shape kinds/fields degrade to fewer things on the canvas, never a broken token.
- **Rule: semantic text lives in cards, not shape labels.** A shape label is chrome; text that matters to the graph gets a card. A lint may suggest promoting a label to a card — suggestion, never prohibition.
- **Dragging a card** = a layout-token update, debounced/coalesced into content ops (no per-mousemove op spam). All writes ride `object.update` — no new sync primitive.
- **Collab caveat (deferred, additive):** the whole layout is one CRDT text; simultaneous drags converge at text level (fine for disjoint edits). If real-time collaboration ever makes that bite, splitting layout into its own CRDT field is an additive change — note it, don't build it now.

## External-id mappings — `external_ref.*` (NORMATIVE, owner requirement 2026-10-23 — the plugin mapping substrate; SHIPPED, three-client converged)

Importers and sync plugins (calendar providers, Readwise, read-it-later) need a durable **external → internal id mapping** — a Google Calendar event UID, a Readwise highlight id, a read-it-later entry id resolving to the notees node uuid — so re-runs **update** the mapped node instead of duplicating it (match by external id, never by title/content). The durable home is the **operation log**: not a device table (derived SQLite DBs are wipe-rebuildable — the mapping would die on rebuild) and not per-user server prefs (the wrong scope — mappings are per-workspace, plugin-owned). Log-carried mappings sync to every device, ride the backup, and converge by LWW.

- **`external_ref.set {ref, nodeId}`** — one LIVE mapping per `ref`, **LWW by envelope (hlc, actor)** on the `(workspace, ref)` key: a re-set **moves** the mapping (re-targeting is legal — a synced item may be re-imported onto a different node), and a racing pair converges on the higher tuple under either delivery order. `ref` is the caller-namespaced key `<provider>:<kind>:<externalId>` (e.g. `gcal:event:abc123@google.com`, `readwise:highlight:12345`) — the protocol does **not** parse the namespace (opaque), but empty or > 512-char refs fail loud (the strict schema). `nodeId` is a bare uuid with **no referential integrity** (the `property_value` precedent): a mapping may name a node another device has not synced yet; the read names a node, it does not guarantee one.
- **`external_ref.delete {ref}`** — the LWW delete side, and it keeps a **tombstone per (workspace, ref)** in the derived state (the `property_value_tombstone` precedent) — **including a delete of an UNMAPPED ref**. The tombstone is what kills a stale concurrent `set` delivered after the winning delete on every replica; without it, delivery order would diverge. At most one of {live row, tombstone} stands per key: a winning set deletes the tombstone, a winning delete deletes the live row.
- **Many refs per node, one node per ref.** The same event synced from Google AND Outlook lands two refs on one node; the reverse read scans the derived table (no reverse payload exists on the wire).
- **Derived state (store schema v30, purely additive):** `external_ref` (PK `(workspace_id, ref)`, `node_id`, envelope causality columns, index on `node_id`) + `external_ref_tombstone` (PK `(workspace_id, ref)`, causality columns). A node's **hard delete purges its live rows** (the `subtreeIds` pattern in the `object.delete`/`trash.empty` appliers — a hard-deleted node leaves no mapping behind); **soft-trash keeps them** (a restore re-activates the node, mappings intact). Ref tombstones survive their node's purge (keyed by ref, they bound garbage to the ref name).
- **Client surface:** reads `resolveExternalRef(ref): nodeId | null` (absent/tombstoned → null) and `externalRefsOf(nodeId): string[]` (sorted); writes `setExternalRef(ref, nodeId)` / `removeExternalRef(ref)`. The web client's read-cache invalidation: `externalRefsOf` is node-scoped (the applier's ChangeSummary carries the mapped node ids — previous + new carrier on a move), `resolveExternalRef` is content-global (its key is an opaque ref string that never appears in an affected set — the `resolveAlias` precedent). The session undo journal inverts both writes through the normal write path (set → delete when the ref was unmapped, else restore of the captured prior carrier; delete → restore of the captured carrier).
- **LOCKSTEP SHIPPED (2026-10-23, the date-chain precedent):** the GTK / Flutter ports vendored `external-ref.json` byte-identical (sha256 `9cf46b1b…45a47e` on all three) and converged their appliers on the same fixture expectations — GTK `23bcc28` (912 tests green), Flutter `fdf14fd` (695 tests green). The store's canonical-fixture test replays the real fixture JSON (forward + reversed mapping delivery + idempotent replay) rather than a hand-built stand-in.

## Node structure — `is_class` × `is_embedded` (NORMATIVE, Revision 12, owner 2026-10-16)

Revision 10's `node_type ∈ {page, block, class}` enumeration and Revision 11's `present_as_main` render bit are replaced by **two booleans** that separate three independent concerns: **classification** (`is_class` — what the node represents), **parent relationship** (`parent_id` — which node it structurally belongs to), and **embedding** (`is_embedded` — whether its content belongs to the parent's body). The render cascade is `is_class → ClassView; parentless → document chrome (flag unread); else the flag decides — and the parent must be a page`:

- **Terminology (the words every surface uses, owner 2026-10-09; the roles re-documented 2026-10-16):** a node has a **structural role** and may or may not be an **entity**. The **Page role** = any node that renders with document chrome — `is_class = 1` (a class), OR `parent_id IS NULL` (a workspace root — no parent, standalone by definition), OR `is_embedded = 0` on a parented non-class node whose **parent also renders with document chrome** (the parent-page condition, owner ruling 2026-10-15). The **Block role** = any other parented non-class node — `is_embedded = 1` (embedded in the parent's body), or the flag inert under a non-page parent (a class or an inline block). An **entity** = a node classified by the system (a meeting, quote, city, person, …) — entity status is independent of the structural role: an entity may be embedded (a minor meeting in Today's page) or standalone (an important meeting as a separate structural element under Today). The domain predicates `rendersWithDocumentChrome` / `rendersAsInlineBlock` (`packages/domain/src/node.ts`) encode exactly the two role branches (the predicates take an optional parent-facts argument; the stored invariant makes it implicit over real data); exports, outlines, section queries, and picker filters all speak this distinction ("child pages" = standalone-zone children, "child blocks" = the embedded body zone). Page/Block remain the user-facing words for the two roles — they are render states of one node kind, never stored kinds.

- **`is_embedded`** — the embedding flag, read ONLY by the third cascade branch (a parented non-class node): `true` (the default) = the node's content is part of the parent's body — the Block role, inline with block chrome, included when the parent's body is rendered or exported; `false` = a standalone structural element under that parent — the Page role, the parent's main-children zone with document chrome (when zoomed), NOT included in the parent's body content. Unread/unused for parentless nodes (standalone by definition — a parentless row's flag is stored but never read, benign by construction, exactly like Revision 11's parentless bit) and classes (ClassView). **Moves never write the flag** (the role survives reparenting).

- **The link-based display transformation (NORMATIVE, owner 2026-10-16; the per-link embedding flag refines it same-day):** a block whose entire content is a link/mention marked **embedded** presents THAT node in its place — the referenced node's content renders inline in the block's place (transclusion-style in the web editor), regardless of the referenced node's structural role. The gate is the LINK's own embedding flag: the `mention` content token carries optional **`isEmbedded`** (the wire shape), and the derived `edge` table projects it as `edge.is_embedded INTEGER NOT NULL DEFAULT 0`. **Embedding is a manual per-link choice — the default is FALSE**: an unmarked link, including every pre-existing link, is an ordinary inline link even when it is its block's whole content; the flag is independent of the node's structural-role `is_embedded`. A block that mixes a link with other content keeps the ordinary content rendering; a block without a link renders normally. The transformation is presentational only — the block's contentAst stays a mention (editing, sync, undo unchanged), and toggling the flag does not change the link's identity (the edge id is content-addressed without it; the flag updates in place like the alias resolution).
- **Display-time horizontal rule (NORMATIVE, owner 2026-10-16):** a block whose content is EXACTLY `---` (one plain text run, no marks, no whitespace tolerance — the domain `isRuleContent` derivation) renders as a horizontal rule at display time; the node is an ordinary text block on the wire and in the store — **zero protocol footprint** — and the rule is purely render state (the web block row renders an `<hr>` and does not render the block's children — a rule terminates a section; the HTML export maps the same derivation to `<hr>`, markdown keeps the literal dashes). Editing the block shows the raw `---` text, and typing anything else turns it back into an ordinary block by construction.

- **The parent-page condition (NORMATIVE, owner ruling 2026-10-15, carried into Revision 12):** a parented node renders with document chrome **only** when `is_embedded = 0` AND its parent renders with document chrome. A class parent is never a page (ClassView), so a standalone claim under a class or an inline block is **inert** — the node renders inline in the parent's body. Impossible states are write-time impossible: the applier fails loud (`MoveGuardError`) when `object.create` or a promotion (`object.update {isEmbedded: false}`) claims the standalone role under a non-page parent, when `object.move` carries an `is_embedded = 0` node under a non-page parent, and when a parented page with `is_embedded = 0` children is demoted (the children would dangle — demote or move them first). **LOCKSTEP SHIPPED (GTK/Flutter v4.1.x-era ports + the CLI's Revision-12 vendor pin b245671)** — the GTK/Flutter ports converge on the `is-embedded-parent-page.json` fixture and the Revision-12 rename before the marker clears (`docs/developers/development.md` §3). Logs written under the old permissive model are normalized by the one-time in-place rewrites `scripts/migrate-main-parent-page.mts` and `scripts/migrate-is-embedded.mts` (kind B, `docs/developers/migrations.md`); historical violating ops replay-quarantine like every other old-era guard breach.
- **`is_class`** — the only identity marker; classes are always roots (`CHECK (is_class = 0 OR parent_id IS NULL)`). Class declaration remains the `class.create` op (declaration-first: users create classes, configure them, and use them later or never).
- The axes are now: **`is_class`** (identity/classification) × **`parent_id`** (placement/parent relationship) × **`is_embedded`** (embedding/structural role) × **`class_ids`** (domain typing — whiteboard, meeting, …). Placement lives only in the tree: a cross-page move updates nothing but the parent edge (+ order) — no cascades.
- **Wire node fields (the icon/color precedent, owner 2026-10-07; `description` joins 2026-10-09):** `object.update` gains three OPTIONAL NULLABLE fields — **`coverAssetId`** (asset node behind the page cover), **`bannerAssetId`** (asset node behind the page banner), **`aliasedNodeId`** (the main page a node alias points at — many-to-one FROM the alias: a node aliases at most one node) — plus **`description`** (the page subtitle in the core page chrome, the Capacities header precedent: plain text, max 512 chars). They are platform-fixed node fundamentals (derived directly as the node-table columns `cover_asset_id` / `banner_asset_id` / `aliased_node_id` / `description`, store schema v18), never class-bound properties; `object.create` carries none of them (defaults NULL), presence writes and present-null clears exactly like `color`. The applier maps without validating — asset existence and alias-chain acyclicity are read/client-layer concerns. The query language gains the matching field predicates for the three reference fields (`coverAsset` / `bannerAsset` / `aliasedNode`, eq/neq/exists over the node-table columns); `description` gains no query predicate yet — free-text grammar is a deliberate follow-up, not a silent default.
- **Per-block list style (NORMATIVE, owner 2026-10-16):** `object.create`/`object.update` gain the OPTIONAL NULLABLE **`listStyle`** — `"numbered" | "alpha" | "roman"`, the bullet dot's replacement on block rows (absent/null = bullet, the zero-migration default; present-null clears, exactly like `color`). It is presentation state, NOT queryable — no query predicate, no applier semantics beyond persistence, and the stored column carries ONLY the style: the marker NUMBER (`1.` / `a.` / `i.`) is derived at render time from the node's position in the contiguous run of same-style siblings directly above it — any sibling without the same style (or a different one) resets the count — computed per sibling group, so nested lists number independently. Derived directly as the node-table column `list_style` (store schema v23). Canonical fixture `object-list-style.json`; **LOCKSTEP SHIPPED 2026-10-20** — the GTK v4.2.0 / Flutter v4.1.0 ports accept the key (strict-payload additive, the wire-fields precedent).
- **`active` — the archival bit (NORMATIVE, owner ruling 2026-10-22, the classes-gallery batch):** `object.update` gains the OPTIONAL boolean **`active`** — `false` ARCHIVES the node, `true` UNARCHIVES it. Archival is a reversible **state**; the trash table is **deletion** (an event) — two lifecycles, never conflated. Platform-fixed, cardinality-1 node fundamental (the icon/color precedent), archived on any node — pages, blocks, classes alike; the class registry `active` is a projection of the class node's bit. Presence writes (absent = no write); the applier projects the bit to `node.is_active`. **The filtering law: every default read is `active = 1` AND no trash row** — collection/query compiler results, graph view, backlinks, the class pills row, node pickers, search, hubs; opt-in "show archived" seams exist only where restore/disable affordances live (the gallery's disabled state, the Archived surface). Canonical fixture `object-update-active.json`; the store-side write path + filter sweep land with the store slice.
- **The retired property schemas are superseded** — cover (`…000000000005`), banner (`…000000000006`), aliasOf (`…000000000029`): their ids stay reserved (history never reuses ids) and nothing seeds or binds them anymore; live property assertions converge onto the wire fields by the one-time script `scripts/migrate-cover-banner-alias.mts` (appended `object.update` + `property.unset`, dry-run default), which also resolves v1-migrated cover data (`{hash}` values → the asset node via the CAS table). **Alias semantics shipped with the client read paths** — the chain walker, write-time cycle validation, the universal redirect, the backlinks roll-up, and graph exclusion all read the node column now (see "Node aliases"). **GTK/Flutter alignment is a separate follow-up in the clients repo** (the new `object.update` keys are additive fields on a strict payload — a pre-batch client rejects them; the lockstep law gates the live migration run).
- Applier defaults for an absent `isEmbedded`: **0 (standalone) when parentless, 1 (embedded) otherwise** — embedded is the default when creating a node. Content flattens to **text-only when `is_class`**; a page's own content keeps the inline tokens it is sent on content writes (rich titles) — create-as-page and promotion still stringify (the lossy boundaries).
- **Promotion/demotion = the `isEmbedded` toggle** (`object.update {isEmbedded}` — one op, in place, identity preserved; promotion stringifies the content). Promotion (isEmbedded: false, the standalone/Page claim) is gated by the parent-page condition (a non-page parent rejects it); demotion of a parented page is gated on its standalone children being gone. **Declaring a class = `class.create`** (classes become containers per spec I4: class nodes may have non-class children; the cross-row guard is now "no class under a class", an applier move-guard, fail-loud — projection rule 1 deleted).
- **Wire (envelope v3):** `object.create`/`object.update` carry optional `isEmbedded`; the strict payload schemas **reject the retired `nodeType` and `presentAsMain` keys outright** — no wire compat of any kind (owner directive: the owner is the sole user). Old stored logs are migrated **in place, once**: `scripts/migrate-node-type.mts` rewrote `nodeType` → `presentAsMain` ("page"→true, "block"→false, "class"→the class.create op) at the v3 bump; `scripts/migrate-is-embedded.mts` rewrites `presentAsMain` → `isEmbedded` (value inverted) and the stored query ASTs (condition values, sort fields, group dimensions) at the Revision-12 bump. Appliers implement **only** the new model: create defaults `isEmbedded ?? (parentless ? 0 : 1)`; content flattens to text-only when `is_class` (pages keep inline rich tokens on content writes; create-as-page and promotion stringify); promotion/demotion = the `isEmbedded` toggle; declaration = `class.create`. Validators accept only `protocolVersion` **3**.
- **Listings:** root documents = `WHERE is_class = 0 AND parent_id IS NULL`; classes = the derived `class_list` read model keyed on `is_class = 1` (applier-maintained, wipe → replay → identical; authority on the node — explicitly NOT a stored registry: no shadow split, no new op type). Nothing else anchors the Classes UI — the retired system `class` meta class (…0001, withdrawn 2026-10-07) is not the predicate and not an anchor.
- **The conversion capability (owner ruling 2026-10-07, retiring the seeded `class` meta class):** `class.create` on an EXISTING node DECLARES that node a class — `is_class` flips to 1, a parented node is cut to a root (the parent edge and its child-order row drop — classes are always roots), the embedding flag clears (`is_embedded = 0`), the registry row adopts the node's existing title (title-is-content: the node row is the authority; a payload `contentAst` still wins LWW), and membership/children are untouched (classes are containers). A bare `{classId}` payload is the whole conversion — no new payload keys (the schema always accepted the id; the capability is applier semantics, pinned by the `class-convert.json` fixture). Re-declaring an existing class is a replace no-op (absent fields preserve, they never wipe). The ruling: nodes bound to the retired class-class become real classes — live workspaces convert by `scripts/migrate-retire-class-class.mts` (class identity touches every client — the GTK/Flutter ports are the lockstep gate).
- **Queries:** "containing page of B" = nearest ancestor that renders with document chrome (parentless or an effective main child — the parent-page condition included); "blocks inside page Y at any level" = subtree CTE from Y joined against the edge index (the `specific_pages` scope port) — read O(subtree), write zero; an ancestor-closure read model is a *derived* optimization only if profiling demands it.
- **Whiteboard:** `whiteboard` system class + content token; fullscreen = parentless (document chrome by the second cascade branch), embedded = a parented inline body child; cards are its children. General rule: what-it-is lives in class, specialized data lives in tokens/assertion rows — never new kinds or flags.

## Node aliases (NORMATIVE, issue #7, owner 2026-10-05; carrier moved to the wire field 2026-10-07)

**Text aliases name a page; node aliases link a page under another.** A page may declare itself an **alias of** a main page. The carrier is the **`aliasedNodeId` wire node field** (SCHEMA.md "Node structure", owner 2026-10-07) — `object.update {aliasedNodeId}` on the alias page, many-to-one FROM the alias (a node aliases at most one node). The `aliasOf` property schema (`…000000000029`) is the retired carrier: its ids stay reserved, live property assertions converge onto the field by `scripts/migrate-cover-banner-alias.mts`, and every read below rides the node column. The relation is **one-way** (alias → main; the main page holds nothing).

- **Restriction to pages — CLIENT-SIDE enforcement, by design (stated honestly):** the web properties panel renders the alias row for document-chrome carriers only (never for inline blocks), the row's picker offers pages only, and the write path validates the target against `rendersWithDocumentChrome`, rejecting anything else with a visible error **without writing**. The applier enforces nothing: any client (or a raw op writer) may author an `aliasedNodeId` pointing anywhere — enforcement is a client convention, exactly like the render contracts (PC1), not an integrity rule. Non-page values then simply don't act as aliases (every read below filters to pages).
- **Write-time cycle validation (the extends-DAG precedent):** `object.update {aliasedNodeId: T}` on node N runs a whole-graph cycle check AT THE APPLIER: the would-be chain N → T → T's target → … is walked before the write, and a revisit of any visited node — N itself included, so the 1-edge self-alias is covered — fails loud (`CycleError`) and is **never applied**. Clearing (null) cannot create a cycle and skips the check. A stale-HLC update is dropped by the row LWW before the check. `Store.resolveAlias(nodeId)` walks the chain to its terminal, cycle-safe by construction (a revisit yields the **starting id unchanged** — a cyclic alias is no alias) with a generous depth cap; `Store.aliasNodesOf(nodeId)` is the reverse read — every live node whose alias-terminal is the node (a recursive reverse-walk over the column, chains included) behind the aliases listing and the unlinked-references exclusion (the linked-references roll-up rides the materialized `resolved_target_id` column instead — "Linked-references roll-up" below).
- **Linked-references roll-up:** the main page's linked-references union — direct backlinks, source-side containment roll-up, AND edges whose target is any page whose alias-terminal is the main page — the last family surfacing as `kind: "alias"` rows. The roll-up rides the **materialized `edge.resolved_target_id` column** (store schema v17): the applier resolves each edge target's alias-terminal — the same cycle-safe chain walk as `resolveAlias`, LIVE-aware (a trashed/deleted node never resolves through; non-page carriers still don't act as aliases — the read filters carriers to pages per the restriction above) — at edge-write time and re-resolves on alias writes and liveness flips (trash/restore/permanent-delete/archival); the backlinks read and the graph probe the column by index. No wire change (derived-only). The alias page's own view is unchanged: it lists only edges targeting the alias itself. `node_stats.backlink_count` (the badge) stays direct-only, so the list may outrun the number — the same accepted badge-vs-list divergence the containment roll-up documents.
- **Derived-schema alignment (GTK/Flutter follow-on):** the TS reference store bumps to schema v17 with this column. The GTK and Flutter stores carry their own derived schemas — their v17 follow-on adds `edge.resolved_target_id` with the identical write-time/re-resolution semantics (their reads may keep walking chains until the bump lands; the column is a derived optimization, not a wire or semantic change). No client lockstep gates this slice.
- **Navigation — the universal redirect:** every open surface resolves node aliases to their terminal — the App open funnels (`openPage`/`openInSidebar`, the floating editors, hover previews, the link context menu) route through `resolveAliasOpen` (the single seam, over `Store.resolveAlias`), so graph node clicks, backlink/query result rows, mention clicks, the command palette, and breadcrumbs all land on the main page (chained aliases collapse to the final main, cycles yield the id unchanged). Links keep the alias uuid at authoring — **no rewriting**; resolution happens at navigation. Opening the alias page **as a node** — the aliases UI's NAVIGATE, deep links — shows the alias's own view (its own body, only its own links) plus an **"Alias of \<main\>"** chip jumping to the main page. Links *of* the alias (its own references) navigate to their targets as usual.
- **The aliases UI:** the main page's title row carries a count/button ("Aliases · N") opening the aliases list — every page whose alias-terminal is the main; each row NAVIGATEs to the alias's own view (the redirect bypass), and ADD picks a page and writes **THE SELECTED node's** `aliasedNodeId` to the main (the backward write — never the active node's own field; the picker filters nodes that already alias something and the main itself, and the page guard validates the pick). The alias's own view carries ONE pseudo-property row — a node-typed **"Aliased node"** entry backed by the field itself, re-pointable (Change) and clearable (present-null) from the alias side.
- **Graph exclusion:** alias nodes are NOT graph vertices; edges incident to an alias render incident to its terminal (A→alias(X) renders A→X), repointed parallels merge into one weighted edge, and the local-scope anchor steps through to the terminal's neighborhood.
- **Name-equivalence:** an alias page's title is one of the main page's names — the unlinked-references pass matches it for the main page (a source that *links* the alias is already linked by alias, so it never lists as unlinked). `resolveNodeByName` resolves an exact alias-page title to the alias page (the mention target it creates is the alias page; navigation resolves it per the rule above); the server's `GET /api/resolve` folds node aliases to the terminal via the same chain walker.
- **Coexistence:** text aliases (`…0028`) and node aliases (the wire field) are independent and may combine: "Cats" as a text alias of **Cat** is just another name; **Cats** as a node alias is a page whose inbound links roll up to **Cat** while its own view stays separate.

## Node merge (NORMATIVE, owner 2026-10-13 — the v1 mergePages port, extended to the v2 model)

**Merging absorbs one node into another.** `merge(source → target)` consolidates the source page into the target page and trashes the source. It is a **client/server-composed gesture of EXISTING op types — there is deliberately NO `object.merge` op**: a merge plans to a deterministic batch of ordinary convergent ops, so every client (web local-first, GTK, Flutter, CLI) converges on it by replay with zero applier changes, the web's undo journal inverts it as one gesture, and the wire stays untouched.

The normative semantics (the TS reference planner is `packages/store` `planMerge`; the server exposes it at `POST /api/objects/:id/merge` with a `?dryRun=true` preview):

1. **Children** — the source's active children move to the target (append, relative order preserved; sequential `object.move` with `afterId` chaining). The source's own title content is NOT carried over — title-is-content means the target keeps its title.
2. **Class & tag bindings** — the target gains each of the source's memberships (the re-issued `object.create` add carrier); the source's memberships tombstone (`class.unassign` / `tag.unassign`). The OR-Set remap is idempotent.
3. **Authored properties** — copy source → target: a **single-value slot copies only when the target has no authored value there** (the target wins; a populated slot is reported as skipped, never overwritten); a **multi-value slot appends the source's value-distinct elements under FRESH PG5 element ids** (element identity is per-row; copying the id would collide). Node references to the source inside copied values/metadata rewrite to the target.
4. **Content links** — every active node's `contentAst` gets its **`mention` tokens pointing at the source retargeted to the target** (`object.update`, the edge index re-derives); nested occurrences (inside `quote`/`heading` children) included. Aliases are not followed here: a mention of an alias of the source keeps pointing at the alias (leg 5 repoints the alias, resolution lands on the target).
5. **Aliases** — every node whose `aliasedNodeId` is the source repoints to the target.
6. **Property references** — node-typed property values (object/asset refs, datetime anchors, date-qualified `startDate`/`endDate` metadata) on ANY active node that reference the source rewrite to the target via `property.set` re-addressing the same element id (LWW overwrite).
7. **Collections** — each collection holding the source gains the target and drops the source (`collection.member.add` / `remove`).
8. **Wire fields** — `coverAssetId` / `bannerAssetId` / `description` copy only when the target's field is empty.
9. **The source trashes last** (`object.delete {permanent: false}`) — every other leg reads source state at plan time and the delete must not precede its own plan's application.

**Guards fail loud BEFORE anything reaches the log** (`MergeGuardError` / 422 `validation_failed`): either node missing or trashed, either node a class, source === target, the target inside the source's subtree (trashing the source would trash the target), or the source a non-empty collection (membership remap into an arbitrary node is out of scope). A merge is a deliberate, previewable gesture: the plan's numeric summary (children moved, bindings/properties/links/aliases/collections remapped, properties skipped) is the `--dry-run` / dialog contract.

## Block → page extraction (NORMATIVE, owner 2026-10-16)

**Extraction converts an inline block into a root page in place — a client-composed gesture of EXISTING op types, deliberately no new op** (the Node merge precedent). One `object.create` (a link block whose whole content is a single `mention` of the extracted node) + `object.move` of the node to the workspace root (identity and content preserved — unlike the `isEmbedded` promotion, an extraction does NOT stringify; the mention's captured `text` is the node's display name at gesture time, non-authoritative) + one `object.move` per reparented child.

1. **The link block takes the block's exact slot** — created under the old parent with `beforeId` THE BLOCK ITSELF: the link lands immediately ahead of the block on every position (first, middle, last — the applier's beforeId midpoint), and the block's departure to the root leaves the link holding its slot. Anchoring against the source beats sibling anchors: the source is always present in the store, where a sibling lookup can miss on a stale cached read and append the link at the end (the 2026-10-16 fix).
2. **The block moves to the workspace root** (`parentId: null`) — a parentless non-class node renders with document chrome per the render-state model.
3. **Children** — in the submenu's default extraction row they STAY in the original page: each active child moves onto the link block in the store's child order (sequential `object.move` with `afterId` chaining, the merge children leg). The **children-follow row carries them over to the extracted page instead** — then legs 1–2 alone land (the link block simply replaces the block; the children never move). The choice is a plain click per row in the web's **Convert to page ›** submenu (no modifier keys — `extractBlockToPage`'s `keepChildren` option is the seam).

Guards fail loud client-side before anything reaches the log: the node must be an inline block (`rendersAsInlineBlock` — a page or class converts nothing) and not a date-chain node (parent-locked, "Datetime" — a root move would fail at the applier's `MoveGuardError` anyway). The web gesture is `extractBlockToPage` (`apps/web/src/core/extractToPage.ts`); the wire stays untouched, so every client converges by replay with zero applier changes.

## Select options: colors + icons (NORMATIVE, PG16 colors owner 2026-10-04; icons 2026-10-05)

A select/multi_select option record is `{ id, label }` plus an **optional `color`** — a preset token or a custom `#RRGGBB` hex; absent/null = no color (additive JSON inside the existing options array — no op-shape change). Clients render the color on the selection pill (themed background, contrast-appropriate foreground — the class-pill convention) and expose a per-option color control in the schema settings; the settings/settings-freeze contract is unchanged (options replace wholesale on `propertySchema.update`, colors included).

**An optional `icon`** — an MDI icon name (camelCase @mdi/js convention, max 64 chars — the same string shape as node/class icons); absent/null = no icon. The option record itself stays **non-strict** on purpose: older parsers strip unknown keys instead of rejecting the envelope, so icon-carrying options sync through old clients (their stores drop the icon; wipe → replay restores it). Clients render the icon wherever the option surfaces — the selection pill, option pickers, and (with the schema `display` position below) the block-bullet value button. Per-option icon editing lives in the schema settings beside the color control.

## Data color grammar (NORMATIVE, owner 2026-10-03)

A node/class `color` (on `object.update` / `class.create` / `class.update` — `object.create` carries no appearance fields) is ONE string field with a strict grammar:

- a **preset token**: exactly one of `red, orange, yellow, green, teal, sky, blue, purple, pink, gray` (the token SET is normative; display order is a client concern — web: hue order then gray);
- or a custom hex **`#RRGGBB`** (exactly 6 hex digits);
- or **`null` to clear** — `object.update` gains the clear with this grammar (the UI's "No color" was a protocol no-op until now); `class.update` documented "null clears" from the start and the schema now accepts what the catalog documented.

The concrete preset hex is **never on the wire** — it lives client-side (web: `variables.css --color-preset-*`; Flutter: `ColorPresets`; GTK resolves nothing — it round-trips the string), so themes remap the palette without touching data. The first v3 encoding stored CSS variable references (`var(--color-preset-red)`); that web-ism leaked onto the wire, drifted between clients (mobile stored resolved hexes), and is **rejected outright** by the strict schemas — stored logs are rewritten **in place, once**, by `scripts/migrate-color-tokens.mts` (var refs AND known legacy preset hexes from the retired ClassView palette and the drifted mobile palette fold to their tokens; other hexes stay custom). Appliers distinguish field **absence** (no write) from **present-null** (clear, writes NULL) — presence checks, not null checks, on the write path. The icon field may embed a color inside its JSON string (`{"icon":"mdiX","color":"sky"}`) — the same grammar applies inside the JSON.

## Projection-reclassification rules (NORMATIVE, 2026-09-25; classed-with-parent rule deleted 2026-10-02 — classes are containers now, spec I4)

In a node's body block-list, exclude direct children that are:

1. **targets of the parent's node-typed property values** — carrier blocks render in the properties panel, not the body; or
2. **`is_embedded = 0`** — standalone children render in the parent's **main-children zone** (they open with document chrome when zoomed), not inline in the body.

Both are derived (the applier recomputes them; wipe → replay → identical), never stored flags. One mechanism, two uses. Everything else about the children — queries, backlinks, `refset` roll-up, focused view — is unaffected.

## Per-user UI state — favorites & recents (NORMATIVE ruling, owner 2026-10-04)

**Favorites and recents are UI preferences, not graph state — they live in the sync server's per-user prefs store, never in the operation log.** The design law "device state is never an op" stands: there is no envelope, no op type, no payload key for them, and no client lockstep (the GTK/Flutter clients have nothing to parse; every client's derived DB semantics are untouched).

- **Store:** the `user_prefs` table on the sync server's relay.db (`user_id` PK → account, `favorites`/`recents` JSON id lists, `updated_at`) — server-side account state like sessions and plugin registry rows, scoped to the authenticated principal (account session or API-key owner; the operator key is not a user).
- **Surface:** `GET /api/me/prefs` and `PUT /api/me/prefs` (merge patch — each present list replaces its column; the client owns ordering). Lists are uuid-shaped node ids, order-preserving dedupe then caps (favorites ≤ 500, recents ≤ 50, most-recent-first).
- **Client contract:** clients read the server copy and write through to a device-local cache (`notees.favorites` / `notees.recents`); offline, the cache answers reads and holds writes for the next sync. The cache keys are the same source the palette's Recent section and the sidebar sections read — one list, one truth per user.
- **Convergence honesty:** last write wins per list; concurrent devices may interleave recents arbitrarily (UI state — approximate recency is acceptable); a device-only local id (written after the last successful push) merges ahead of the server's recents on load, never clobbers.

## System sections

Predefined page sections are **named system queries** over the QueryAST runtime (the `autoFixSystemQuery` pattern), not bespoke UI: **linked references, unlinked references, child pages, classed nodes, extended-by** ship with fixtures like any op type, and the section registry is plugin-extensible (with the plugin runtime). Owed: the system-query registry, section fixtures, and the per-section projection rules above wired in.

Section specs and the lazy-loading contract:

- **Unlinked references — pages only.** Literal-text appearances of the page's name (and of every name-equivalent — text alias values, alias-page titles "Node aliases") anywhere in the workspace, **excluding** blocks that already link to it (already-linked = the linked-references set — a link to any of the page's alias pages counts as linked by alias). Implemented as an FTS query over the page name (the `unlinked_references` system query). Blocks do not get this section.
- **Linked references for blocks — right-gutter toggle.** A block with backlinks shows a button to the right of the block element containing the link count (`node_stats.backlink_count` — materialized, so the badge renders unconditionally and is exempt from the lazy-loading contract). Toggling it expands the linked-references system query scoped to that block, rendered inline beneath it; the query runs on first toggle and caches until an invalidating notification, per the contract.
- **Linked references roll-up (pages):** the list unions three families, direct first: edges targeting the page; outward edges from inside the page's subtree (containment); and edges targeting any alias page of the page (any node whose alias-terminal is the page — `kind: "alias"`, "Node aliases"). The badge (`node_stats.backlink_count`) counts the first family only — the list may legitimately outrun the number.
- **Lazy-loading contract (all system sections):** collapsed by default, and a collapsed section executes **no query** — nothing loads until first expand (the `QuerySection` pattern). Count badges come only from materialized derived counts (`node_stats.backlink_count` for linked references); **unlinked references shows no eager count** — computing the count *is* the expensive query. Results cache per section until an invalidating notification lands (content/class/property edge changes).

## Class properties — bindings, defaults, aggregation (NORMATIVE, owner philosophy 2026-09-27)

Classes define **bound property schemas** (with per-binding metadata). Nodes with the class get the property's schema-level default **applied**; nodes with several classes **aggregate** the bindings; removing a class removes its bound properties **that have no authored value** (authored values always survive — design law).

- **Bindings are configuration rows carrying ONLY the per-class mechanic left — the soft-unbind flag** (`class_property`: `active` — owner ruling 2026-10-20, the property-definition surfaces batch; `sequence` retired 2026-10-21), authored by two ops: `class.property.set {classId, propertySchemaId, active?}` (upsert) and `class.property.unset {classId, propertySchemaId}` (remove the binding). Class property panels render as a PURE ALPHABETICAL list everywhere (by property name, derived at read time — nothing on the wire or in the store carries order). Applier-maintained registry; binding writes are ordinary config ops (LWW on the row by HLC; omitted fields keep their stored values). `required` and `defaultValue` LEFT the binding under the owner ruling 2026-10-20 — `required` retired outright (its only render effect, hiding the icon-button's "None" row, was mild enforcement contradicting the render-contract law), `defaultValue` moved to the property schema (below); the strict binding schema rejects both keys like any retired key and live logs rewrite in place via `scripts/migrate-drop-binding-required.mts` (Path B — see `docs/developers/migrations.md`). `sequence` joined them 2026-10-21 (owner ruling — pure alphabetical rendering made panel order unconfigurable): the strict binding schema rejects the key outright and live logs rewrite in place via `scripts/migrate-drop-binding-sequence.mts` (a plain in-place strip, no compensation). The render contracts (`hideWhenEmpty`, `display`; `readonly` joined the retired set 2026-10-21) had already moved property-level (owner review 2026-10-05, `scripts/migrate-binding-flags-to-schema.mts`). `readonly` was never user configuration — no seed ever carried the flag — so it DERIVES from the system property list instead of storing (`isReadonlyProperty`, packages/domain): the strict schemas reject the retired key outright and live logs rewrite in place via `scripts/migrate-drop-schema-readonly.mts`.
- **`scopeClassIds` is the SOLE locality authority (owner ruling 2026-10-20, R1 — the property-definition surfaces batch):** a property schema carries `scopeClassIds` (`propertySchema.create/update`) — absent/null = **global** (any node may carry the property), a non-empty class-id list = **local** to those classes AND their extends-ancestors (the empty array is rejected: exactly one spelling of "global"). This RETIRES the display-only `scope: "global" | "class" | "object"` enum — the strict schemas reject the retired key outright and live logs rewrite in place via `scripts/migrate-property-scope.mts` (Path B; `"global"` → the key stripped, `"class"` → the one-element seed/bindings class list, `"object"` → global + owner report). Bindings carry **zero** availability semantics — two orthogonal axes: *scope says who MAY carry the property; a binding says whether a class LISTS it* (`active`). `citekey` is local to `source` + extensions per the seed; `status` stays assignable anywhere (global scope — the seed-scope audit below).
- **Eligibility is extends-aware (R2)** and enforced **fail-loud at write time (R3)**: a node is eligible when it carries a scope class or an ancestor of one (the same `class_hierarchy` closure binding resolution walks). `property.set` on an ineligible node rejects at the applier (`MoveGuardError`); schema-less writes (unknown schema id) stay unchecked. Narrowing a scope later never orphans history — pre-existing authored rows survive in the log and the effective read returns them tagged `eligible: false` (enforcement is never retroactive).
- **The effective read gates too (R4):** an ineligible node shows neither the property nor a derived default from an out-of-scope binding — `getEffectiveProperties` tags every row `eligible: boolean` (additive; `eligible: false` only on authored rows whose schema excludes the node; derived defaults never materialize for ineligible nodes, so they always read `true`). Authored rows on ineligible schemas SURVIVE and read back tagged — callers decide rendering (the web picker/panel gating is slice-3 work).
- **Dead config is rejected (R5):** `class.property.set` on a schema whose scope excludes the binding class fails loud (the binding would be provably inert under R4) — a subclass-of-scope class binds fine (its closure reaches the scope class through the ancestor). This does NOT make bindings a locality mechanism; it just refuses nonsense rows.
- **The schema's base-definition fields (`propertySchema.create/update`, owner ruling 2026-10-20):** create gains `icon` (nullable MDI name), `scopeClassIds`, and `defaultValue` (the global default, PC2-validated against the payload's type); update gains `icon`, `scopeClassIds`, `targetClassFilter`, `multi`, `validationRules`, and `defaultValue` (PC2-validated against the STORED type) — all nullable with the keep/clear contract (absent keeps the stored value, present-null clears). `validationRules` is `{min?, max?, pattern?}`: `min`/`max` apply to `number` schemas only, `pattern` to `text`/`url`/`email` only (enforced at APPLY time against the stored type — the update payload carries no type), and `min <= max` is a parse-time rule. **Value enforcement SHIPPED 2026-10-20 (the R2 companion, TS reference):** a schema carrying stored rules validates every `property.set` value BEFORE the write and fails loud — `min`/`max` bound a number schema's value (inclusive `>=`/`<=`, checked AFTER the legacy numeric-string normalization), `pattern` full-string-tests `text`/`url`/`email` SCALAR values (implicit anchors, the HTML `pattern` semantics — a text carrier ref `{nodeId}` is not a string and rides unchecked); each multi element is its own `property.set`, so one bad element add rejects its op while the surviving elements stay. Rule-free schemas and schema-less writes (unknown schema id) stay unchecked. A `propertySchema.update` carrying a **non-compilable `pattern` fails loud at the rule write** — a stored pattern that threw at value-check time would be an applier crash, which is never acceptable. LOCKSTEP SHIPPED 2026-10-20 (GTK v4.2.0 + Flutter v4.1.0, fixtures 36/36 byte-identical); the live migration ran the same day and the stack redeployed — VERIFY-PASS.
- **`active` is the soft-unbind flag (PC4, DONE 2026-10-04 as the TS reference, LOCKSTEP SHIPPED same day — GTK/Flutter v3.0.0):** LWW on the binding row. An INACTIVE row stops contributing to the effective-properties read entirely while the row survives and AUTHORED property values always survive (they read as unbound, `boundBy` null). Unlike `class.property.unset` (which deletes the row), disable keeps the row for a later re-enable.
- **Render contracts are PROPERTY-level (owner review 2026-10-05 — supersedes the binding-level field the same day it shipped; `readonly` retired 2026-10-21):** a property schema carries `display` (`"panel" | "bullet" | "inline"`) and `hideWhenEmpty` — nullable tri-state fields on `propertySchema.create/update` (absent keeps, null clears; the keep/clear contract of the number formats). `readonly` left the payloads entirely (owner ruling 2026-10-21): an enumeration of the seeds finds ZERO system properties that ever carried the flag — it was never user configuration — so clients DERIVE readonly-ness from the system property list (`isReadonlyProperty`, packages/domain: the platform-provenance schemas `generatedFrom` + `alias`, fixed seed UUIDs) exactly where the old flag dimmed/disabled editors. The strict schemas reject the retired key outright; live logs rewrite in place via `scripts/migrate-drop-schema-readonly.mts`. They answer "what the property is and how it behaves **everywhere it appears** — whatever class binds it, or none" (an unbound property like `alias` carries them too). `display` says where a **select/multi_select or boolean** value renders on a block row: **"panel"** (the default) keeps the value in the properties section only; **"bullet"** renders it as an icon button next to the block bullet; **"inline"** renders the same button immediately before the block content (the Logseq-DB "UI position: beginning of the block" behavior; the `icon_visibility` port). The button shows the current option's icon tinted with its color (booleans render the same shape as two synthetic options — true = a check-circle, false = a hollow circle, the owner-specified glyphs) and opens a small picker — the state reads at a glance and changes inline. The picker's "None" row always clears (`required` retired outright, owner ruling 2026-10-20 — see PC1 below). All three are a **render contract only**: no applier or query reads them beyond persistence; properties displayed at bullet/inline are de-duplicated out of the block's properties section (the button surfaces the value in context — the original rule). The setting UI gates the display control to select/boolean types. The seeded task **Status schema carries `display: "bullet"`** (owner-mandated task-status glyphs: circle-family icons, yellow pending / blue review / red cancel / green done).
- **The DEFAULT VALUE is SCHEMA-level (owner ruling 2026-10-20 — the Logseq shape):** a property has ONE global default, carried by `propertySchema.create/update {defaultValue}` (nullable, the keep/clear contract: absent keeps, present-null clears — the cleared spelling is SQL NULL, never a stored JSON null). It moved from the per-class binding: a per-class default was configuration creep the class page never needed, and the class-level inline editor is gone with it (the class page lists its properties, Logseq-style; the default editor lives in the base-definition modal). The PC2 type table below is unchanged.
- **Defaults are a DERIVED read model — never materialized writes.** The applier does NOT create `property_value` rows for defaults. The effective value is computed at read time: `effective(node, schema, idx) = authored property_value ?? the schema's defaultValue`, materializing only when a winning ACTIVE binding brings the property into the node's context. This gives convergence for free (no default-write CRDT semantics), makes cleanup free, and keeps the authored/derived boundary honest: editing a default in the UI writes an authored `property.set`, which from then on shadows the default.
- **Aggregation**: the effective bindings of a node = the union of bindings across ALL its classes. Per `(schema, idx)`, binding-metadata conflicts (which class supplies `boundBy`) resolve first-class-applied wins (below); the schema-level default and render contracts have no per-class variance by construction.
- **Conflict resolution — first-class-applied wins** (binding attribution only — the default value itself is schema-global since the owner ruling 2026-10-20): among the node's classes that bind the same schema, the winner is the class whose membership assignment (the OR-Set add) has the **earliest HLC**; ties break by class id. Deterministic on every replica.
- **`extends`-aware resolution (DONE 2026-10-03, PG4)**: the diamond rule is implemented at read time in the effective read model — candidates are (class, ancestor) pairs discovered by a shortest-path walk over `class_extends` (own binding = distance 0), the winner minimizing (extends-distance, class-assignment HLC, class id). A subclass node therefore **inherits its ancestors' bindings** (`boundBy` naming the ancestor whose row supplies them) — a runtime `source` subclass inherits the `authors`/`attachments` bindings without re-binding. The `class_hierarchy` closure carries no distance, so the walk uses the edge table.
- **System-class extends is FROZEN to the seeded set (owner ruling 2026-10-22 — the system-extends lock):** a system class's extends mapping is seeded platform structure, and TWO product behaviors derive from it — the feature-toggle cascade (`systemClassAncestors`, `packages/domain`: disabling `event` archives `meeting`/`birthday`/`trip` with it) and binding inheritance (the `class_extends` walk above). A user edit would silently diverge the toggle's assumptions from the store's actual hierarchy, so `class.setExtends` on a system class applies ONLY when the payload's parent set EQUALS the seeded set (compared as sets) — the seed/ensure re-issue convergence path (`apps/server/src/seed.ts`, the web `deploySystemClass`/`meetingFamily` ensures). Every deviation — detaching a seeded parent, adding an extra parent, attaching parents to a system class with none — fails loud with `SystemExtendsLockError` and is never applied. User classes stay freely extensible, including onto system bases (a runtime subclass of `source`/`meeting` is the designed extension point). Enforcement is never retroactive: a pre-lock deviation already in a stored log stands (the lock gates new writes only). The web class page's extends corner renders READ-ONLY for system classes (static pills — no add/remove chrome); fixture `class-extends-system-lock.json` pins the accepting prefix (user→system extension + the seeded re-issue) and the rejecting tail.
- **Render flags are a RENDER CONTRACT, not write enforcement (PC1, SCHEMA statement 2026-10-03; `required` retired 2026-10-20, `readonly` 2026-10-21):** `hideWhenEmpty`/`display` (per-property schema) and the derived readonly-ness are client-honored by design law — no applier or write-path enforcement exists for them (that would police usage, not integrity). The convention: **readonly** (derived from the system list since 2026-10-21) dims/disables the property's editors (never blocks a write); **hideWhenEmpty** hides the row unless a value or a derived default exists. Clients render them uniformly (web: the page properties panel + the property settings + the Class View). The designed `required` highlight/lint never shipped, and the flag's one real behavior — hiding the icon-button's "None" row — was mild enforcement contradicting this law, so the owner ruling 2026-10-20 retired it outright (the strict binding schema rejects the key; live logs rewrite via `scripts/migrate-drop-binding-required.mts`).
- **`defaultValue` is typed and validated (PC2, DONE 2026-10-03; the write path moved to the schema 2026-10-20):** `propertySchema.create` validates `defaultValue` against the payload's type, `propertySchema.update` against the schema's STORED type (the update carries no type; a schema-less write stores unchecked) — both **fail loud** on mismatch. Node-typed schemas (`datetime`, `object`, `asset`) accept only JSON null — a default that links a node is meaningless; `text`/`url`/`email`/`image`/`select` take strings, `number` a finite number, `boolean` a boolean, `multi_select` an array of strings. A stored default that drifted out of match (schema delete+recreate under the same id with a different type) yields **no default** at the effective read instead of a wrong-typed value.
- **Class removal**: an unassign simply removes the class from `class_member_set` — bound properties with **no authored value** stop being derived (nothing stored, nothing to clean: "non-value properties get removed" is automatic); properties the user **did** set keep their authored rows and remain visible (marked as unbound-by-current-classes in the panel).
- **Node-level ASSIGNMENT is first-class log state (owner ruling 2026-10-23 — the v1 `node_property` table lineage):** a node may carry a property **without a value** — assign now, set the value later. Three ops author the declaration: `property.assign {objectId, propertySchemaId}` (upsert a presence row per (node, schema), LWW by the full (hlc, actor) tuple — the `class_property` row precedent; a schema-less write stores unchecked), `property.unassign {objectId, propertySchemaId}` (plain DELETE — the `class.property.unset` precedent), and `property.empty {objectId, propertySchemaId}` (clear **every** authored value of the property on the node while KEEPING the declaration — the "Empty property" gesture; the assigned-empty row renders again, a bound default resurfaces). Assignment carries **ZERO availability semantics** — `scopeClassIds` stays the sole locality authority, so the applier enforces the same R3 eligibility check as `property.set` (a scoped schema rejects an ineligible node, fail loud); `property.set`/`property.unset` stay legal WITHOUT an assignment (values never require a declaration); `property.unassign` removes the declaration only — **authored values survive** (never retroactive: they render as ordinary unbound authored rows). `property.empty` causality mirrors the per-value removes applied to each live row: BOTH tombstone families upsert at the empty's (hlc, actor) — the PG5 element tombstone and the legacy slot tombstone — so older adds at **observed** slots stay dead either carrier (a concurrent NEWER set survives); adds at slots the empty never touched ride the house add-wins rule. Orphaned exclusive text carriers ride the unset's trash contract. The derived table is `node_property` (schema v29); the effective read synthesizes **empty rows** for a node with nothing on the slot — `value: null`, `source: "assigned"` for the node's own pin, `source: "bound"` (`boundBy` naming the binder) for the class's VIRTUAL contribution (owner ruling 2026-10-23, the virtual/realized assessment — "they should still show up as coming from the class"; scalar types included, the bound-empty panel pass having covered grouped types only) — panel/chrome only, invisible to queries and exports, suppressed when the schema is deleted or `hideWhenEmpty`, gated by R4 (a scope narrowed after the bind shows neither row nor default), and shadowed the moment a value or default exists (an empty row never coexists with authored carriers; an assigned row wins the slot over a bound one — the declaration is the node's own). **Unrealize (`property.unassign`) on a class-bound property drops only the pin — the binding still supplies the property, so the row keeps rendering as `bound`.** Ordering: empty rows ride the main alphabetical block; only unbound **authored** rows sort last. LOCKSTEP-PENDING (GTK/Flutter converge on `property-assign.json`, byte-identical fixtures); old logs replay unchanged — no migration. Fixture: `property-assign.json`.
- **Read surfaces** use effective values: the store exposes `getEffectiveProperties(nodeId)` (authored + derived rows + assigned-empty rows, each tagged `source: "authored" | "default" | "assigned"` and `boundBy: classId`); the property panel renders derived defaults distinctly (dimmed) until edited and assigned-empty rows as empty editable cells; queries/tables read through the same function.
- Fixture-first: `class.property.set` ships with a canonical fixture (bindings on two classes + the SCHEMA-level default → a node of either class reads the same global default; unassign one binding → the other still derives it; unassign both → nothing derives; unassign the CLASS → derived default gone, authored value survives).

## Node-backed text properties (NORMATIVE, 2026-09-25; write-path contract + lifecycle 2026-10-03)

- The `text` value type is **node-typed by convention**: `property.set` stores a carrier block's id; the properties panel renders an editor that writes content ops to the carrier — so property text carries the **full grammar** (mentions, class links, typed links, embeds) and may have an **arbitrary number of children at arbitrary depth** (it is a block; the panel edits it as a mini-outliner, focused view opens it).
- Carrier blocks are **real children of the owner node** (`parent_id = owner`; containment derives from the tree — no placement fields) → containment, backlinks, `refset` roll-up, queries, and export resolution all work. The carrier's own children are ordinary blocks under the carrier; the body-exclusion rule filters only direct carriers, **computed per subtree root** — a nested block's own carriers are excluded from *its* body, and an excluded carrier's whole subtree is pruned with it.
- **One-shape-per-type at the write path (PB2, DONE 2026-10-03)**: the store validates `property.set` values against the schema type and fails loud on mismatch. A `text` slot takes a **scalar string** (the seeded source family carries citekey/isbn/publisher as plain strings) or a carrier reference `{ "nodeId": … }` — never a number/boolean/array. `datetime`/`object`/`asset` take node references (a legacy bare-uuid string normalizes to `{nodeId}`; a date-looking string is rejected — dates are nodes): a datetime POINT `{ "nodeId": <chain node>, "time"?: "HH:MM" }` or a RANGE `{ "start": slot|null, "end": slot|null }` where a slot is `{ "nodeId": …, "time"?: "HH:MM" }` — either side open; the legacy `date`/`date_range` value shapes are legal members of the union (SCHEMA.md "Datetime"). Schema-less writes (unknown schema id — `property.set` has no schema FK) store unchecked.
- **Unset deletes the carrier** (trash + retention, consistent with node deletion). The applier trashes the carrier **only when the removed value references a node that is an active non-class child of the owner and no other property_value row still references it** (same carrier in two slots, or referenced from another node → the unset detaches and leaves it). Scalar text values carry no carrier. **"Promote to block" is a separate gesture** — detach the value and revive the carrier as an ordinary body child; clients compose it from the two existing ops (`property.unset`, whose applier trashes the orphaned carrier, then `object.restore`, a safe no-op when a reference kept it alive). Display state only: no move op, no new wire.
- **Auto-unset of contentless values (client behavior, owner ruling 2026-10-09):** a text value whose carrier has no content and no child blocks is unset by the client (the properties panel) instead of lingering as an empty block — the slot returns to its empty state and the unset's carrier-trash reclaims the orphaned block. A dead reference whose target node is gone counts as contentless (unset); a ref that still resolves to a node that merely stopped rendering inline (promoted to a page) keeps its recovery cell. No op, no wire change, no fixture gate: the panel emits the ordinary `property.unset`, so every replica converges from the log as usual.
- **Multi-value element identity + OR-Set (PG5, DONE 2026-10-04 as the TS reference, LOCKSTEP-PENDING — supersedes the PB4 positional-slots model)**: a multi-value slot is an **OR-Set of elements**, each with a stable per-element id. `property.set` on a multi schema carries a writer-minted **`elementId`** (UUIDv7 — identity law); the `property_value` row id **IS** the element id, so adds of distinct elements never conflict and concurrent adds at the same `idx` **coexist** (visible order = `(idx, element id)`; `idx` is a per-element order hint, writers allocate it, gaps never heal — the PB4 tolerance stands). `property.unset {elementId}` is the OR-Set remove: the applier tombstones the element (`property_value_element_tombstone`, strictly-greater full `(hlc, actor)` upsert — the `class.unassign` convention) and deletes the live row when the remove's **HLC** is strictly newer — **add-wins: on equal HLC the add wins regardless of actor** (the membership comparator is HLC-only; the classIds `>=` convention generalized to the two-table projection). A re-issued add with a not-strictly-older HLC revives the element. **Single-value slots stay LWW at the element** (one deterministic element per slot). A payload WITHOUT `elementId` is the **legacy positional carrier** (pre-PG5 clients, replayed stored logs): it addresses the deterministic positional element `node:schema:idx` with the pre-PG5 slot tombstones — and a positional `unset` suppresses the whole slot positionally (newer element adds at that idx survive). The visible set (live rows minus slot tombstones minus element tombstones) is derived ONCE (`visiblePropertyValueRows`, `packages/store/src/property-values.ts`) and every read consults it: the effective model, the edge index, the FTS plaintext, the store/API reads, and the query compiler (its SQL carries the same suppression predicate). The pre-v11 `UNIQUE(node, schema, idx)` is retired (schema v11, additive rebuild): per-element identity makes same-idx rows legal.
- Multi-value `text` = m2m list of carrier block ids, each with its own subtree.

- **Broken references (PB1, owner ruling 2026-10-04 — keep-value + render-broken)**: a node-typed property value whose target is deleted or trashed **keeps the value** — no cascade delete/clear (the mention policy, Fork 4). The edge projection keeps the derived edge: `rebuildEdges` derives from the surviving value rows, never from target liveness, and must not drop a broken ref silently; the permanent-delete applier keeps incoming edge/node_link rows from surviving sources (deleting them only to have the next rebuild re-derive identical rows was the transient-resurrection bug). Clients render the broken state honestly: the pill shows the raw id with a broken affordance (SCHEMA Fork 4's rule), never a silently empty chip.

## Datetime — the unified date property type (NORMATIVE, owner 2026-09-27; unified 2026-10-09)

The `date` and `date_range` property types are retired and unified into ONE **`datetime`** type (2026-10-09): the strict `propertySchema.create` enum rejects the retired values outright; live logs rewrite in place by `scripts/migrate-unified-datetime.mts` (migrations.md Path B — envelope ids/HLCs unchanged, values untouched since every legacy shape is a legal member of the new union).

- **A date is a node, not a string.** Datetime property values reference the workspace's **year / month / day node chain** (system classes `year`/`month`/`day`, deterministic UUIDs from the date — the `generate_day_uuid` scheme, ported to `@notees/domain`). Setting a date **auto-creates the chain** (year node, month node under it, day node under that — deterministic ids make the creates idempotent no-ops on existing nodes). Dates thereby participate in the graph for free: backlinks on a year node list everything dated that year; journals are ordinary trees of day nodes.
- **Date-chain nodes are parent-locked (owner 2026-10-13):** a date node's parent IS its deterministic chain parent — year at the workspace root (`parentId: null`), month under its year, day under its month, nothing else. `object.move` with any other parent **fails loud** (`MoveGuardError` — the same guard class as the class-no-parent rule; a move onto the chain-correct parent stays legal, which the client chain self-heal rides). `object.create` **claiming** any other parent fails loud the same way; a parentless create is the tolerated standalone shape the self-heal adopts onto the chain. **All three implementations carry the guard** (TS reference + GTK + Flutter, 2026-10-13 — the lockstep is complete).
- **Date-chain nodes are class-locked (owner 2026-10-13):** a date node's class set IS its precision's system class — year nodes carry `year`, month nodes `month`, day nodes `day`, nothing else, and a date node is never declared a class. `object.create`'s classIds OR-Set carrier (the `class.assign` add path, re-issued creates included) with a foreign class and `class.unassign` of the precision's system class **fail loud** (`MoveGuardError`); `class.create` on a date id fails loud outright. Unassigning a FOREIGN class stays legal — cleanup of a legacy violation, not a lock breach. The web classes row renders read-only on date nodes, and the `+` class capture / `/checkbox` task assignment never fire on them. **All three implementations carry the guards** (TS reference + GTK + Flutter, 2026-10-13 — the lockstep is complete).
- **The value union** (one shape per value, enforced fail-loud at the applier):
  - **point**: `{ "nodeId": <chain node id> }` — a legacy `date` value rides untouched (full-day); **`timed point`**: `{ "nodeId": <day node id>, "time": "HH:MM" }**.
  - **range**: `{ "start": <slot|null>, "end": <slot|null> }` where a **slot** is `{ "nodeId": …, "time"?: "HH:MM" }` — either side open; a legacy `date_range` value (bare refs, open sides) rides untouched.
  - **Full-day = the absence of `time`** — the default for every new value; no separate boolean is stored.
  - `time` is 24h wall-clock local at minute precision with **no timezone**; `time` requires **day precision on BOTH the schema ceiling and the slot's ref** (a year/month anchor has no wall-clock time) and must match `/^([01]\d|2[0-3]):[0-5]\d$/`.
  - A value carrying BOTH `nodeId` and `start`/`end` keys is **rejected outright** (fail loud); a malformed `time` is rejected.
  - Multi-value elements: each element independently point-or-range.
- **Precision scoping**: a datetime property schema declares `datePrecision: "year" | "month" | "day"` (default `"day"`). year-precision links the YEAR node; month links the MONTH node. Values never claim finer granularity than the schema allows; a `time` always rides a day anchor.
- **Number formats (display-only, 2026-10-04)**: a number property schema may declare `numberPad` (zero-pad the integer part to N digits — the Pokédex "#0001" case), `numberDecimals` (digits after the point, 0–10), and `numberRounding` (`round` half-away-from-zero — the default when only decimals is set — `floor`, `ceil`, `truncate`). Values stay **exact in the log**; these shape render only, and rendering ignores them for non-number types. `propertySchema.update` keeps absent fields and clears with explicit `null` (the keep-vs-clear contract).
- **Link qualifiers (dates for links)**: a node-typed property schema may set `dateQualified: true`; then each value may carry `metadata.startDate` / `metadata.endDate` as **date-node refs through the chain** (PC6, DONE 2026-10-04 as the TS reference — the schedule-BEFORE-data-accrues ruling; writers ride the `ensureDateChain` pattern, refs stay existence-lenient until the chain exists). **Migration tolerance:** the pre-PC6 ISO-string encoding reads lenient everywhere (panel, export) and **normalizes on write** — the applier rewrites a well-formed `YYYY-MM-DD` string on a dateQualified schema to the deterministic day-node id (the bare-uuid precedent; only the two reserved keys, only dateQualified schemas, pure value rewriting — no graph side effects). A qualifier's precision is the ref's chain precision (year/month/day node id). The properties panel renders the small range control next to qualified link chips.
- **Recurrence (compute-on-read — owner ruling 2026-10-04):** a datetime value may carry a recurrence rule in `metadata.repeat` — additive metadata, the startDate/endDate precedent; **no new op, no wire change**. See "Recurrence" below. Recurrence stays day-anchored: the value's own day is the series anchor; a `time` rides a timed series' display, never its expansion.
- **Query semantics**: date-bound comparisons (eq/contains/relational) compare the anchor and **ignore `time`** — a timed point sorts with its day; range eq/contains = bound within [start, end] (open side = unbounded); relational ops compare the range START (period-start semantics, the existing cross-precision rule). `{today}`-style placeholders stay date-only.
- **Picker UX**: one datetime picker with **zoom levels** — a year grid, a month grid, a day grid — switching freely between them; the precision ceiling is the schema's (a year-precision property zooms months/days only to show context, committing at year). Ranges use the picker per end. **Slice 2 (2026-10-09 ruling) aligns the layout to the reference:** a suggestions column (Yesterday / Today / Tomorrow / In 1 week / In 2 weeks), an **All-day** toggle (default ON; off reveals the time input — the `time` presence), a **Range** toggle (off default; on reveals the end slot), and a **Remove** action; month grid with month ⌄ / year ⌄ dropdowns and ‹ › navigation.
- **Storage/convergence**: values are ordinary property JSON (`time` rides the value — no new columns); the chain creation rides the op log (client-emitted creates, deterministic ids); edge projection treats datetime refs like node-typed values (backlinks/journals).
- [x] **Protocol↔query dependency cycle** — DONE 2026-09-27: the zod AST model moved from `packages/query/src/ast.ts` to `packages/protocol/src/query-ast.ts` (the wire-adjacent home — the content grammar's `query` token embeds it, so protocol must not depend on query). `packages/query/src/ast.ts` is now a thin re-export from `@notees/protocol`, so every `import { … } from "@notees/query"` path (apps, compiler/dsl/executor) is unchanged; query runtime-depends on protocol, protocol depends on no workspace package. ## Recurrence — RRULE-lite on date values, compute-on-read (NORMATIVE, owner ruling 2026-10-04)

A **recurring event is ONE node**: its date value carries the rule, and the calendar expands **virtual occurrences at read time**. The owner spec ruling (the compute-on-read option): **no new op type, no wire change, no fixture gate, no client lockstep** — the rule is additive value metadata, exactly like the startDate/endDate qualifiers. Occurrences are **never materialized as nodes** (design law: no hidden objects); editing the event edits the series.

- **Storage**: `metadata.repeat` on the date property value, holding the canonical grammar string. The value's own day IS the series **anchor** — the anchor is never stored inside the rule (one source of truth: the linked day node). Precision coarser than day has no anchor and MUST NOT carry a rule.
- **Grammar** (the stored form, fail-loud parse — `@notees/domain` `parseRecurrenceRule` throws on anything else): `<freq>` or `<freq>/<interval>`; `<freq>` ∈ `daily` | `weekly` | `weekdays` | `monthly` | `yearly`; `<interval>` = integer 2..999 (1 is the default, never written; an explicit `/1` normalizes away). `weekdays` (Mon–Fri) rejects an interval. Clients that don't know the key ignore it — the value stays an ordinary date ref.
- **Expansion semantics** (`occurrenceIsosOf(series, fromIso, toIso, cap?)`, inclusive window): the anchor day is occurrence #0. `daily` = every interval days; `weekly` = every interval weeks on the anchor's weekday; `weekdays` = every Mon–Fri; `monthly` = the anchor's day-of-month every interval months — a month lacking that day (Jan 31 → February) **skips**, RRULE-style; `yearly` = the anchor's month-day every interval years (Feb 29 skips non-leap years, the same rule). Expansion is **capped** (default 366 occurrences): a window wider than the cap **truncates** — callers size the window instead of expecting completeness. A present-but-corrupt rule throws (fail loud — corrupt metadata never reads as "does not repeat").
- **Reads**: calendar surfaces enumerate the workspace's recurring values (a scan of effective date values — occurrences have no materialized hook), then expand per window. The day view's Dated/Tasks sections list a recurring row on every occurrence day with an honest repeats marker (one row per series, never phantom rows); a repeating task schedules on occurrence days and is **never overdue** (missed occurrences roll forward). The month grid dots every occurrence day (anchor-day dots compose with the materialized backlink read).
- **Per-occurrence completion**: a recurring TASK's done-toggle in a day context records the occurrence, not the series — `metadata.completedOccurrences` on the recurring date value holds the completed days (local ISO `YYYY-MM-DD` strings, sorted, deduped; absent = none; present-but-corrupt throws, the fail-loud idiom). The toggled occurrence renders done on its day while every other occurrence stays open; reopening removes just that date; the `repeat` rule and any qualifiers ride through untouched. No nodes are materialized — occurrences stay virtual. Writers that don't know the key read an ordinary date value (convergence neutral).
- **Recurrence exceptions** (the Google-calendar edit/delete semantics, owner 2026-10-23 — additive metadata on the SAME date value, the `completedOccurrences` precedent; no op, no wire change): acting on ONE occurrence of a series asks the scope — *only this event* / *this and following events* / *all events*. Two keys carry the exception state, read fail-loud (absent/null = default, present-but-malformed throws):
  - `metadata.exdates` — occurrence days removed from the series: a single deleted occurrence, or a day whose occurrence was EDITED into an exception node (a new ORDINARY event — content/classes/authored properties copied, a plain non-repeating date at the edited day — Google's detached-instance semantics; the series skips the original day). Sorted ISO days, deduped.
  - `metadata.until` — the inclusive last occurrence day: the bound a *this-and-following* split writes (`until` = the last series occurrence before the split day; occurrences after it do not exist). A continuation node carries the edited values forward with the SAME rule from its new anchor (a fresh series — it does not inherit the bound; exdates at or after its anchor move with it). When the acted-on day IS the anchor (no earlier occurrence exists), *this and following* degenerates to *all events*. Expansion honors both keys (`recurrenceSeriesOf` assembles the full input; `occurrenceIsosOf` skips exdates and stops past `until`).
  - The exception node is the ONLY materialization this model ever creates — one ordinary event per edited occurrence, never per occurrence at large; deleting an occurrence materializes nothing (the day joins `exdates`). Children stay on the series (an exception is the node's own row; sub-blocks belong to the series).
- **Multi-day spans (the datetime-range ruling, owner 2026-10-23):** a datetime value whose own day is the inclusive START may carry `metadata.endDate` — a local ISO `YYYY-MM-DD` day, additive metadata like `repeat` (no op, no wire change). The value keeps referencing its START day node; the span expands CLIENT-SIDE at read time (the compute-on-read register — `spannedRowsOf` in the web client covers every day in `[start, end]` in the events read model, the grid blocks, and the day dots). An `endDate` equal to or before the start day reads as a plain single-day value. Corrupt metadata throws (fail loud); writers that don't know the key read an ordinary date value (convergence neutral).
- **Scope limits (documented)**: the shipped picker authors interval-1 rules (the grammar accepts intervals for API/CLI writers). Typed-link target resolution stays the owner-deferred design — a verb MARK on a word has no target; the targeted path a bound verb participates in is a property VALUE over the bound schema (verb = propertySchemaId in the edge index), which surfaces in the target's backlinks named by the schema.

- [x] **Plugin manifest grammar** — DONE 2026-10-04: the manifest is DECLARED vocabulary, not an op carrier — registry rows are server state, not log state (the prefs/shares ruling), so there is no envelope, no op type, no fixture gate, and no client lockstep. The normative grammar is the "Plugin manifest grammar" section below; the zod schema (`packages/protocol/src/plugin-manifest.ts`) is its executable form; the server registry (`/api/plugins*`) and the web Plugins tab manage inert rows. The plugin RUNTIME (capability broker, subprocess host, manifest consumption) is explicitly PARKED: `capabilities`, `entrypoint`, and `permissions` are validated and stored, never executed or enforced.

## Plugin manifest grammar (NORMATIVE, owner 2026-10-04 — SCHEMA + REGISTRY SHIPPED, RUNTIME PARKED)

A **plugin manifest** is a versioned, strict JSON document a plugin author declares; the host stores and displays it now, and the (parked) runtime will consume it later. `manifestVersion: 1` is the grammar version — additive fields amend the strict schema; a breaking change bumps the literal (a protocol-batch decision). Unknown keys are rejected outright (strict; the no-backward-compatibility owner directive applies).

- **Identity law:** `id` is a lowercase reverse-domain (`com.example.notes`) OR a UUID; `version` is strict semver 2.0.0; the registry keys on the **(id, version)** pair (install is idempotent on it — a repeat install answers the existing row; the same id at a different version is 409, versioned updates ride the runtime). `name`/`description`/`author` are attributes, never identity.
- **`capabilities`** (all optional, all declared-only — declaring grants nothing until the runtime exists): `exportFormats: [{id, label, mime}]` · `importers: [{id, label, mime, mode: "file" | "text"}]` · `commands: [{id, label}]` · `widgets: [{id, label}]` (widgets is the least-designed member — ids/labels only, no renderer contract until the runtime design fixes it). Capability ids are lowercase slugs.
- **`entrypoint`** (reserved): a relative path (no leading slash, no `..` traversal), stored only — NEVER executed by the shipped registry; nothing reads it back into a loader.
- **`permissions`** (reserved): a subset-list over the plugin permission vocabulary — the API scope set plus the two plugin-era additions (`events.subscribe` — durable event delivery; `network` — explicit egress, off by default). Validated now; enforcement is entirely runtime-era (a parked runtime enforces nothing).
- **Registry state:** the sync server stores `{manifest JSON, enabled flag, installed_at}` per (id, version) in a `plugin` table on relay.db (server state — the operation log is untouched; verified by test). Management routes `GET/POST /api/plugins`, `DELETE /api/plugins/:id`, `POST /api/plugins/:id/enabled` are owner/admin-scoped (operator key or administrator account; a scoped API key needs the `admin` scope — the first enforcement of that reserved name). The web surface is Workspace Settings → Plugins (list, capability summary, enable toggle, paste-JSON install with client-side validation).

## Templates — `has-template`, instantiation, link-vs-clone (NORMATIVE, T1/T2, 2026-10-03)

A **template** is an ordinary node carrying the seeded `template` system class (…0001-000000000013) — fully editable with the real outliner, linkable, taggable, findable in the graph. There is no template node kind (design law). **`has-template`** (fixed UUID `00000000-0000-0000-0000-000000000026`) is the node-typed, `multi: true` property **on class nodes** (`targetClassFilter: ["template"]`, seeded spec): a class's bound templates are the authored values on the class node itself. **M47 (2026-10-07): the schema is GLOBAL scope with no class binding** — the retired `class` meta class used to host the binding (the only "every class" host there was); values are authored on class nodes directly and read through the effective-properties authored rows (the aliasOf precedent). Owner decisions: **D1** relation lives on the class, multi; **D2** template-wins precedence (below); **D3** embeds stay live; **D4** daily-note templates parked.

- **Instantiation = client-side clone composition — no template op type.** The clone engine walks the template subtree depth-first over the store's position-ordered children and composes only existing carriers: one `object.create` per cloned node — fresh UUIDv7 identity per node, `contentAst` copied, `classIds`/`tagIds` seeded on the create — followed by the cloned node's authored `property.set` carriers. Sibling order is reproduced identically on every backend by **anchor chaining**: the first cloned child appends; each following sibling carries `afterId` = the previously cloned sibling's fresh id (`parentId` + the m2 `beforeId`/`afterId` carriers; no fractional-order client logic, identical replay on every replica from the single global log).
- **Instantiate-at-create semantics (create-with-template):** the flow first creates the object (picked class, page placement); the template's root is then **grafted onto the created object** — the object receives the root's `contentAst`, its class assignments minus the `template` marker class, its tags (both re-issued via the OR-Set add carrier), and its **authored** property values; the root's children are cloned beneath the object in order. The template node itself is never referenced by the instance.
- **Link vs clone (A3) — references are links, never duplicated:**
  - `mention`, `class_link`, `typed_link` tokens keep their target (rename-safe link semantics; Fork 3/Fork 4 unchanged).
  - Tags are **re-issued** on the fresh id (`object.create`'s `tagIds` OR-Set add — add-wins per pair).
  - Class assignments are copied **minus the `template` marker class** (the strip rule: an instance is not a template).
  - Node-typed property values (m2o/m2m `{nodeId}` refs, incl. date-chain refs) copy the reference.
  - `asset_ref` re-points at the **same CAS asset**; `embed_ref` carries the **same live embed** (D3 — never deep-clone the embedded subtree; the embed rule above stands).
  - `whiteboard` layout `cards` geometry is re-keyed to the cloned cards' fresh ids (geometry follows the re-identified children; shapes/strokes are identity-free and copy unchanged). Every other token copies unchanged.
  - Derived class-binding **defaults are never materialized** onto the instance (the derived read model recomputes them from the instance's own classes).
- **D2 — the template wins per property; `defaultValue` fills only what the template leaves unset.** Template-authored values land as authored `property.set` rows on the instance, so the effective read (`authored ?? winning binding defaultValue`) shows template values over binding defaults **by construction**, and every property the template leaves unset stays live to later binding-default edits. Both are per-class configuration; the template instance copies the binding set by copying the class assignments.
