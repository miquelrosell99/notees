## Content grammar (NORMATIVE, firmed 2026-09-25)

A block node's content is **one flat, ordered token array** (`contentAst: ContentToken[]`). There are no block-level "segments" — paragraph spacing, quotes, queries, whiteboards, assets, and embeds are all tokens in the same stream. The design law applies: nothing prohibits where a token may appear; rendering defines presentation.

Decisions recorded with the grammar:

- **Fork 2 — marks are attributes** on text runs (`marks: ["bold","italic","strike","highlight","code"]`), not nested nodes. Overlaps (a bold phrase containing a mention, a typed-link word in italics) split runs at boundaries — standard rich-text mechanism; no nesting interaction matrix.
- **Fork 3 — `class_chip` is render-only** (owner decision): inserting/deleting a chip does NOT mutate `class_ids`; it references the class node and renders its *current* name (rename once, every chip updates). Assignment is a separate gesture; a lint may suggest it. One-off wording via optional `displayText`.
- **Fork 4 — `mention` stores id only**; display resolves the target's current name at render time (auto-rename free). `text` (captured surface form) is non-authoritative; `displayText` overrides per-link ("the Republic"); broken targets render the raw id (v1 fallback rule).
- **Line breaks (owner decision, 2026-09-25):** exactly one break token — `hard_break` = shift+enter, a line jump inside a block. **Enter always creates a new node** (a new bullet); there is no paragraph concept within a block and no `paragraph_break` token.
- **Prose mode** (bullets hidden, indents flattened) is a VIEW transform, not content.

## The token view record (NORMATIVE, §34.31 V3, 2026-10-04)

The `query` token's optional `view` record is the saved view's persisted configuration. The protocol grammar keeps it a **free-form record** (`z.record(z.unknown())` — additive by construction: foreign keys ride along, newer writers must not break older readers, writers merge into the existing record and never replace it). The disciplined shape (web client reader/writer: `apps/web/src/ui/queryViewRecord.ts`):

- `mode: "list" | "table"` — the result rendering (list default; anything unknown reads back as list).
- `title?: string` — the saved view's display name (ViewTabs; absent = the positional "Query N" fallback). A saved view is otherwise anonymous — title-is-content names NODES, not views.
- `isDefault?: boolean` — the section opens on this saved view (the per-surface default is configuration in the record, not code). One token per section carries the flag.

Reserved for future writers (readers must tolerate them; no current writer emits them): `columns`, `sort`, `groupBy`, `pageSize` (the §34.32 PG9 property-column ride). A version key is intentionally absent — the free-form record IS the versioning mechanism (unknown keys ignore forward-compatibly).

Query blocks are the saved-view vehicle: the token is content, so a saved query rides the op log — synced, local-first, no view entity, no new op. The Queries hub hosts workspace-level saved views as tokens on an ordinary page (§34.31 V1/V4).

## Query compile-time placeholders (NORMATIVE, §34.31 C4/V2, 2026-10-04)

The QueryAST carries **explicit ids only** — no editor-relative id placeholders ("this page" is baked at write time by the builder as a `subtree` scope; the once-reserved `currentNodeId` compile option was dead and is removed). `{today}`-style **date placeholders** ARE ordinary strings in two positions, resolved to concrete dates at compile time against the run clock (`@notees/query` `CompileOptions.now`, default the current instant — a saved view re-evaluates on the day it runs):

- `{today}`, `{this_week}` (ISO week, Monday start), `{this_month}`, `{this_year}`;
- `createdAfter`/`createdBefore` timestamps: the placeholder resolves to the period's local-day boundary expressed in UTC (`created_at` is UTC on the wire) — After floors at the local day start, Before ceilings at the local day end (both inclusive, matching the ops);
- property-condition comparison values (`eq`/`neq`/`gt`/`gte`/`lt`/`lte`): the placeholder resolves to the period start as a plain `YYYY-MM-DD` date — the hand-typed shape, so the ISO-date arms (including the date-node-ref containment match) apply. `contains` (text-substring) and unknown `{...}` tokens never resolve — they stay literal.

## Whiteboard modeling (NORMATIVE, 2026-09-26)

- **Cards are child blocks of the whiteboard node** — full grammar (mentions, chips, typed links), backlinks, search indexing, focused view, classing. The whiteboard is a **spatial view of its subtree**: geometry (`x, y, w, h` per card) lives in the layout token **keyed by node id**; the tree holds content, the token holds geometry. The outliner can render the same children as bullets — same nodes, three views (spatial / outline / focused).
- **Shapes (rectangles, circles, connectors, freehand strokes) are layout-token-only** — pure geometry, no identity, no node overhead. The web toolset's shape set (rect/ellipse/line/arrow/text) plus per-shape `color` and `strokeWidth` and per-stroke `color`/`width`/`highlight` ride the same layout JSON: colors follow the §34.43 data-color grammar (preset token or `#RRGGBB`), widths are world units. Card color is NOT geometry — it is the node color field (§34.43). Client layout parsers stay migration-tolerant: unknown shape kinds/fields degrade to fewer things on the canvas, never a broken token.
- **Rule: semantic text lives in cards, not shape labels.** A shape label is chrome; text that matters to the graph gets a card. A lint may suggest promoting a label to a card — suggestion, never prohibition.
- **Dragging a card** = a layout-token update, debounced/coalesced into content ops (no per-mousemove op spam). All writes ride `object.update` — no new sync primitive.
- **M3 collab caveat (deferred, additive):** the whole layout is one CRDT text; simultaneous drags converge at text level (fine for disjoint edits). If real-time collaboration ever makes that bite, splitting layout into its own CRDT field is an additive change — note it, don't build it now.

## Node structure — `is_class` × `present_as_main` (NORMATIVE, Revision 11, owner 2026-10-02)

Revision 10's `node_type ∈ {page, block, class}` enumeration is replaced by **two booleans**; the render cascade is `is_class → ClassView; parentless → document chrome (bit unread); else the bit decides`:

- **`is_class`** — the only identity marker; classes are always roots (`CHECK (is_class = 0 OR parent_id IS NULL)`). Class declaration remains the `class.create` op (declaration-first: users create classes, configure them, and use them later or never).
- **`present_as_main`** — a render bit read ONLY by the third cascade branch (a parented non-class node): `true` = render in the parent's main-children zone with document chrome (when zoomed); `false` = inline body with block chrome. Unread/unused for parentless nodes — one partition bit for every parent type (the "hide from body" gloss). **Moves never write the bit**; parentless-with-bit-set is benign by construction.
- The axes are now: **`is_class`** (identity) × **`parent_id`** (placement) × **`present_as_main`** (render) × **`class_ids`** (domain typing — whiteboard, meeting, …). Placement lives only in the tree: a cross-page move updates nothing but the parent edge (+ order) — no cascades.
- Applier defaults for an absent `presentAsMain`: **true when parentless, false otherwise**. Content flattens to **text-only when `is_class` or `present_as_main`**.
- **Promotion/demotion = the `presentAsMain` toggle** (`object.update {presentAsMain}` — one op, in place, identity preserved; promotion stringifies the content). **Declaring a class = `class.create`** (classes become containers per spec I4: class nodes may have non-class children; the cross-row guard is now "no class under a class", an applier move-guard, fail-loud — projection rule 1 deleted, spec §10).
- **Wire (envelope v3):** `object.create`/`object.update` drop `nodeType` and gain optional `presentAsMain`; the strict payload schemas **reject the retired `nodeType` key outright** — no wire compat of any kind (owner directive, 2026-10-02: the owner is the sole user). Old stored logs are migrated **in place, once**, by a planned one-time script (`scripts/migrate-node-type.mts`) that rewrites `nodeType` → `presentAsMain` ("page"→true, "block"→false, "class"→the class.create op) and bumps the rewritten rows to v3. Appliers implement **only** the new model: create defaults `presentAsMain ?? (parentless ? 1 : 0)`; content flattens to text-only when `is_class OR present_as_main = 1`; promotion/demotion = the `presentAsMain` toggle; declaration = `class.create`. `protocolVersion` bumps to **3** and validators accept only 3.
- **Listings:** root documents = `WHERE is_class = 0 AND parent_id IS NULL`; classes = the derived `class_list` read model keyed on `is_class = 1` (applier-maintained, wipe → replay → identical; authority on the node — explicitly NOT a stored registry: no shadow split, no new op type). The reserved system `class` node remains as hierarchy root / Classes-UI anchor, not the predicate.
- **Queries:** "containing page of B" = nearest ancestor that is parentless or presents as main; "blocks inside page Y at any level" = subtree CTE from Y joined against the edge index (v1 `specific_pages` scope port) — read O(subtree), write zero; an ancestor-closure read model is a *derived* optimization only if profiling demands it.
- **Whiteboard:** `whiteboard` system class + content token; fullscreen = parentless (document chrome by the second cascade branch), embedded = a parented inline body child; cards are its children. General rule: what-it-is lives in class, specialized data lives in tokens/assertion rows — never new kinds or flags.

## Aliases (NORMATIVE, §34.32 PG10, owner ruling 2026-10-04)

The register contradiction (the v2 post-mortem deemed `node_alias` obsolete while the v1-parity register lists "Aliases (pages)") resolves to the **v1-parity side**: aliases are back as a seeded **multi-value `text` property schema** at the fixed UUID `…000000000028`, GLOBAL scope with **no class binding** — aliases are page metadata, and "page" is not a class in the render-state model, so any binding would narrow aliases to one class's members. (v1 stored aliases in a table, never a property — the uuid is new, not ported.)

## Select options: colors + icons (NORMATIVE, §34.32 PG16 colors owner 2026-10-04; §34.89 icons 2026-10-05)

A select/multi_select option record is `{ id, label }` plus an **optional `color`** in the §34.43 grammar — a preset token or a custom `#RRGGBB` hex; absent/null = no color (additive JSON inside the existing options array — no op-shape change). Clients render the color on the selection pill (themed background, contrast-appropriate foreground — the class-pill convention) and expose a per-option color control in the schema settings; the settings/settings-freeze contract is unchanged (options replace wholesale on `propertySchema.update`, colors included).

**§34.89 adds an optional `icon`** — an MDI icon name (camelCase @mdi/js convention, max 64 chars — the same string shape as node/class icons); absent/null = no icon. The option record itself stays **non-strict** on purpose: pre-§34.89 parsers strip unknown keys instead of rejecting the envelope, so icon-carrying options sync through old clients (their stores drop the icon; wipe → replay restores it). Clients render the icon wherever the option surfaces — the selection pill, option pickers, and (with the schema `display` position below) the block-bullet value button. Per-option icon editing lives in the schema settings beside the color control.

## Data color grammar (NORMATIVE, owner 2026-10-03, §34.43)

A node/class `color` (on `object.update` / `class.create` / `class.update` — `object.create` carries no appearance fields) is ONE string field with a strict grammar:

- a **preset token**: exactly one of `red, orange, yellow, green, teal, sky, blue, purple, pink, gray` (the token SET is normative; display order is a client concern — web: hue order then gray);
- or a custom hex **`#RRGGBB`** (exactly 6 hex digits);
- or **`null` to clear** — `object.update` gains the clear with this grammar (the UI's "No color" was a protocol no-op until now); `class.update` documented "null clears" since M1 and the schema now accepts what the catalog documented.

The concrete preset hex is **never on the wire** — it lives client-side (web: `variables.css --color-preset-*`; Flutter: `ColorPresets`; GTK resolves nothing — it round-trips the string), so themes remap the palette without touching data. The first v3 encoding stored CSS variable references (`var(--color-preset-red)`); that web-ism leaked onto the wire, drifted between clients (mobile stored resolved hexes), and is **rejected outright** by the strict schemas — stored logs are rewritten **in place, once**, by `scripts/migrate-color-tokens.mts` (var refs AND known legacy preset hexes from the retired ClassView palette and the drifted mobile palette fold to their tokens; other hexes stay custom). Appliers distinguish field **absence** (no write) from **present-null** (clear, writes NULL) — presence checks, not null checks, on the write path. The icon field may embed a color inside its JSON string (`{"icon":"mdiX","color":"sky"}`) — the same grammar applies inside the JSON.

## Projection-reclassification rules (NORMATIVE, 2026-09-25; classed-with-parent rule deleted 2026-10-02 — classes are containers now, spec I4)

In a node's body block-list, exclude direct children that are:

1. **targets of the parent's node-typed property values** — carrier blocks render in the properties panel, not the body; or
2. **`present_as_main = 1`** — main-presenting children render in the parent's **main-children zone** (they open with document chrome when zoomed), not inline in the body.

Both are derived (the applier recomputes them; wipe → replay → identical), never stored flags. One mechanism, two uses. Everything else about the children — queries, backlinks, `refset` roll-up, focused view — is unaffected.

## Per-user UI state — favorites & recents (NORMATIVE ruling, owner 2026-10-04, §34.61 on §34.29 #8)

**Favorites and recents are UI preferences, not graph state — they live in the sync server's per-user prefs store, never in the operation log.** The design law "device state is never an op" stands: there is no envelope, no op type, no payload key for them, and no client lockstep (the GTK/Flutter clients have nothing to parse; every client's derived DB semantics are untouched).

- **Store:** the `user_prefs` table on the sync server's relay.db (`user_id` PK → account, `favorites`/`recents` JSON id lists, `updated_at`) — server-side account state like sessions and (§34.59) plugin registry rows, scoped to the authenticated principal (account session or API-key owner; the operator key is not a user).
- **Surface:** `GET /api/me/prefs` and `PUT /api/me/prefs` (merge patch — each present list replaces its column; the client owns ordering). Lists are uuid-shaped node ids, order-preserving dedupe then caps (favorites ≤ 500, recents ≤ 50, most-recent-first).
- **Client contract:** clients read the server copy and write through to a device-local cache (`notees.favorites` / `notees.recents`); offline, the cache answers reads and holds writes for the next sync. The cache keys are the same source the palette's Recent section and the sidebar sections read — one list, one truth per user.
- **Convergence honesty:** last write wins per list; concurrent devices may interleave recents arbitrarily (UI state — approximate recency is acceptable); a device-only local id (written after the last successful push) merges ahead of the server's recents on load, never clobbers.

## System sections (v1 port, M1 requirement)

Predefined page sections are **named system queries** over the QueryAST runtime (v1 `autoFixSystemQuery` pattern), not bespoke UI: **linked references, unlinked references, child pages, classed nodes, extended-by** ship with fixtures like any op type, and the section registry is plugin-extensible (M3). Owed: the system-query registry, section fixtures, and the per-section projection rules above wired in.

Section specs and the lazy-loading contract:

- **Unlinked references — pages only.** Literal-text appearances of the page's name anywhere in the workspace, **excluding** blocks that already link to it (already-linked = the linked-references set). Implemented as an FTS query over the page name (v1 `unlinked_references` system query). Blocks do not get this section.
- **Linked references for blocks — right-gutter toggle.** A block with backlinks shows a button to the right of the block element containing the link count (`node_stats.backlink_count` — materialized, so the badge renders unconditionally and is exempt from the lazy-loading contract). Toggling it expands the linked-references system query scoped to that block, rendered inline beneath it; the query runs on first toggle and caches until an invalidating notification, per the contract.

## Class properties — bindings, defaults, aggregation (NORMATIVE, owner philosophy 2026-09-27)

Classes define **bound property schemas** (with per-binding metadata and a `defaultValue`). Nodes with the class get the defaults **applied**; nodes with several classes **aggregate** the bindings; default conflicts resolve **first-class-applied wins**; removing a class removes its bound properties **that have no authored value** (authored values always survive — design law).

- **Bindings are configuration rows carrying ONLY the per-class mechanics** (`class_property`: sequence, required, defaultValue, active — §34.90, owner review 2026-10-05), authored by two ops: `class.property.set {classId, propertySchemaId, sequence?, required?, defaultValue?, active?}` (upsert) and `class.property.unset {classId, propertySchemaId}` (remove the binding). Applier-maintained registry; binding writes are ordinary config ops (LWW on the row by HLC; omitted fields keep their stored values, `null` clears the tri-state `required`). The render contracts (`readonly`, `hideWhenEmpty`, `display`) are **property-level** and live on the schema (below) — the strict binding schema rejects them; live data moved via `scripts/migrate-binding-flags-to-schema.mts` (see `docs/developers/migrations.md`).
- **`active` is the soft-unbind flag (PC4, DONE 2026-10-04 as the §34.57 TS reference, LOCKSTEP-PENDING):** LWW on the binding row. An INACTIVE row stops contributing to the effective-properties read entirely — no derived default, no required/sequence metadata — while the row survives and AUTHORED property values always survive (they read as unbound, `boundBy` null). Unlike `class.property.unset` (which deletes the row and loses its configuration), disable keeps sequence/default/flags for a later re-enable.
- **Render contracts are PROPERTY-level (§34.90, owner review 2026-10-05 — supersedes the §34.89 binding-level field the same day it shipped):** a property schema carries `display` (`"panel" | "bullet" | "inline"`), `readonly`, and `hideWhenEmpty` — nullable tri-state fields on `propertySchema.create/update` (absent keeps, null clears; the keep/clear contract of the number formats). They answer "what the property is and how it behaves **everywhere it appears** — whatever class binds it, or none" (an unbound property like `alias` carries them too). `display` says where a **select/multi_select or boolean** value renders on a block row: **"panel"** (the default) keeps the value in the properties section only; **"bullet"** renders it as an icon button next to the block bullet; **"inline"** renders the same button immediately before the block content (the Logseq-DB "UI position: beginning of the block" behavior; the v1 `icon_visibility` port). The button shows the current option's icon tinted with its color (booleans render the same shape as two synthetic options — true = a check-circle, false = a hollow circle, the owner-specified glyphs) and opens a small picker — the state reads at a glance and changes inline. `required` is the deliberate exception and stays on the binding (per-class: a property may be mandatory for one class, optional for another). All four are a **render contract only**: no applier or query reads them beyond persistence; properties displayed at bullet/inline are de-duplicated out of the block's properties section (the button surfaces the value in context — the v1 rule). The setting UI gates the display control to select/boolean types. The seeded task **Status schema carries `display: "bullet"`** (owner-mandated task-status glyphs: circle-family icons, yellow pending / blue review / red cancel / green done).
- **Defaults are a DERIVED read model — never materialized writes.** The applier does NOT create `property_value` rows for defaults. The effective value is computed at read time: `effective(node, schema, idx) = authored property_value ?? winning binding's defaultValue`. This gives convergence for free (no default-write CRDT semantics), makes cleanup free, and keeps the authored/derived boundary honest: editing a default in the UI writes an authored `property.set`, which from then on shadows the default.
- **Aggregation**: the effective bindings of a node = the union of bindings across ALL its classes. Per `(schema, idx)`, binding metadata conflicts (required/sequence) resolve the same way as defaults — first-class-applied wins; the schema-level render contracts have no per-class variance by construction.
- **Conflict resolution — first-class-applied wins**: among the node's classes that bind the same schema with a default, the winner is the class whose membership assignment (the OR-Set add) has the **earliest HLC**; ties break by class id. Deterministic on every replica.
- **`extends`-aware resolution (DONE 2026-10-03, §34.32 PG4)**: the diamond rule is implemented at read time in the effective read model — candidates are (class, ancestor) pairs discovered by a shortest-path walk over `class_extends` (own binding = distance 0), the winner minimizing (extends-distance, class-assignment HLC, class id). A subclass node therefore **inherits its ancestors' bindings** (default + required metadata, `boundBy` naming the ancestor whose row supplies them) — a runtime `source` subclass inherits the `authors`/`attachments` bindings without re-binding. The `class_hierarchy` closure carries no distance, so the walk uses the edge table.
- **Render flags are a RENDER CONTRACT, not write enforcement (PC1, SCHEMA statement 2026-10-03; re-homed §34.90)**: `required` (per-class binding), `readonly`/`hideWhenEmpty`/`display` (per-property schema) are client-honored by design law — no applier or write-path enforcement exists for them (that would police usage, not integrity). The convention: **readonly** dims/disables the property's editors (the flag never blocks a write); **required** renders an empty-value highlight plus a lint *suggestion* (suggestion only, never enforcement); **hideWhenEmpty** hides the row unless a value or a derived default exists. Clients render all four uniformly (web: the page properties panel + the property settings + the Class View).
- **`defaultValue` is typed and validated (PC2, DONE 2026-10-03)**: `class.property.set` validates `defaultValue` against the schema type at apply time and **fails loud** on mismatch. Node-typed schemas (`date`, `date_range`, `object`) accept only JSON null — a default that links a node is meaningless; `text`/`url`/`email`/`image`/`select` take strings, `number` a finite number, `boolean` a boolean, `multi_select` an array of strings. A stored default that drifted out of match (schema delete+recreate under the same id with a different type) yields **no default** at the effective read instead of a wrong-typed value.
- **Class removal**: an unassign simply removes the class from `class_member_set` — bound properties with **no authored value** stop being derived (nothing stored, nothing to clean: "non-value properties get removed" is automatic); properties the user **did** set keep their authored rows and remain visible (marked as unbound-by-current-classes in the panel).
- **Read surfaces** use effective values: the store exposes `getEffectiveProperties(nodeId)` (authored + derived rows, each tagged `source: "authored" | "default"` and `boundBy: classId`); the property panel renders derived defaults distinctly (dimmed) until edited; queries/tables (M2) read through the same function.
- Fixture-first: `class.property.set` ships with a canonical fixture (binding with default → node of the class reads the default; multi-class conflict → first-applied wins; unassign → derived default gone, authored value survives).

## Node-backed text properties (NORMATIVE, 2026-09-25; write-path contract + lifecycle 2026-10-03)

- The `text` value type is **node-typed by convention**: `property.set` stores a carrier block's id; the properties panel renders an editor that writes content ops to the carrier — so property text carries the **full grammar** (mentions, class chips, typed links, embeds) and may have an **arbitrary number of children at arbitrary depth** (it is a block; the panel edits it as a mini-outliner, focused view opens it).
- Carrier blocks are **real children of the owner node** (`parent_id = owner`; containment derives from the tree — no placement fields) → containment, backlinks, `refset` roll-up, queries, and export resolution all work. The carrier's own children are ordinary blocks under the carrier; the body-exclusion rule filters only direct carriers, **computed per subtree root** — a nested block's own carriers are excluded from *its* body, and an excluded carrier's whole subtree is pruned with it.
- **One-shape-per-type at the write path (PB2, DONE 2026-10-03)**: the store validates `property.set` values against the schema type and fails loud on mismatch. A `text` slot takes a **scalar string** (the seeded source family carries citekey/isbn/publisher as plain strings) or a carrier reference `{ "nodeId": … }` — never a number/boolean/array. `date`/`object` take node references (a legacy bare-uuid string normalizes to `{nodeId}`; a date-looking string is rejected — dates are nodes). `date_range` takes `{ "start": ref|null, "end": ref|null }`. Schema-less writes (unknown schema id — `property.set` has no schema FK) store unchecked.
- **Unset deletes the carrier** (trash + retention, consistent with node deletion). The applier trashes the carrier **only when the removed value references a node that is an active non-class child of the owner and no other property_value row still references it** (same carrier in two slots, or referenced from another node → the unset detaches and leaves it). Scalar text values carry no carrier. **"Promote to block" is a separate gesture** — detach the value and revive the carrier as an ordinary body child; clients compose it from the two existing ops (`property.unset`, whose applier trashes the orphaned carrier, then `object.restore`, a safe no-op when a reference kept it alive). Display state only: no move op, no new wire.
- **Multi-value element identity + OR-Set (PG5, DONE 2026-10-04 as the §34.57 TS reference, LOCKSTEP-PENDING — supersedes the PB4 positional-slots model)**: a multi-value slot is an **OR-Set of elements**, each with a stable per-element id. `property.set` on a multi schema carries a writer-minted **`elementId`** (UUIDv7 — identity law); the `property_value` row id **IS** the element id, so adds of distinct elements never conflict and concurrent adds at the same `idx` **coexist** (visible order = `(idx, element id)`; `idx` is a per-element order hint, writers allocate it, gaps never heal — the PB4 tolerance stands). `property.unset {elementId}` is the OR-Set remove: the applier tombstones the element (`property_value_element_tombstone`, strictly-greater full `(hlc, actor)` upsert — the `class.unassign` convention) and deletes the live row when the remove's **HLC** is strictly newer — **add-wins: on equal HLC the add wins regardless of actor** (the membership comparator is HLC-only; the classIds `>=` convention generalized to the two-table projection). A re-issued add with a not-strictly-older HLC revives the element. **Single-value slots stay LWW at the element** (one deterministic element per slot). A payload WITHOUT `elementId` is the **legacy positional carrier** (v1 + pre-PG5 clients, replayed stored logs): it addresses the deterministic positional element `node:schema:idx` with the pre-PG5 slot tombstones — and a positional `unset` suppresses the whole slot positionally (newer element adds at that idx survive). The visible set (live rows minus slot tombstones minus element tombstones) is derived ONCE (`visiblePropertyValueRows`, `packages/store/src/property-values.ts`) and every read consults it: the effective model, the edge index, the FTS plaintext, the store/API reads, and the query compiler (its SQL carries the same suppression predicate). The pre-v11 `UNIQUE(node, schema, idx)` is retired (schema v11, additive rebuild): per-element identity makes same-idx rows legal.
- Multi-value `text` = m2m list of carrier block ids, each with its own subtree.
- **Apply-time value validation (PG6, DONE 2026-10-04)**: `property.set` fails loud at the applier on a value that violates the schema's contract — one-shape-per-type (above), the scalar family (`number` = finite number — a numeric string is the v1-migrated legacy encoding and normalizes; `boolean` = boolean; `url`/`email`/`select` = string; `multi_select` = array of strings; `image` stays unchecked until PG14 defines its shape), the multi cardinality ceiling (a single-value schema takes idx 0 only), the `datePrecision` ceiling (a ref may not claim finer granularity than the schema's), the `targetClassFilter` (a date/object ref's target must carry one of the filter classes), and target existence (a date/object/date_range ref must resolve to a node row — trash is a state, not an absence). Text carrier refs stay existence-lenient (legacy encodings ride the log); unknown schema ids store unchecked (no schema FK). Validation is integrity, not usage prediction (PC1's render contract stays client-honor).
- **Broken references (PB1, owner ruling 2026-10-04 — keep-value + render-broken)**: a node-typed property value whose target is deleted or trashed **keeps the value** — no cascade delete/clear (the mention policy, Fork 4). The edge projection keeps the derived edge: `rebuildEdges` derives from the surviving value rows, never from target liveness, and must not drop a broken ref silently; the permanent-delete applier keeps incoming edge/node_link rows from surviving sources (deleting them only to have the next rebuild re-derive identical rows was the transient-resurrection bug). Trashed targets therefore keep backlinks for free, and a restored target heals its backlink set because the rows survived. Ghost-target rows are inert — every edge query is keyed by a live node id. Clients render the broken state honestly: the pill shows the raw id with a broken affordance (SCHEMA Fork 4's rule), never a silently empty chip.

## Dates — year/month/day nodes, precision, ranges, link qualifiers (NORMATIVE, owner 2026-09-27)

- **A date is a node, not a string.** Date property values reference the workspace's **year / month / day node chain** (system classes `year`/`month`/`day`, deterministic UUIDs from the date — v1's `generate_day_uuid` scheme, ported to `@notees/domain`). Setting a date **auto-creates the chain** (year node, month node under it, day node under that — deterministic ids make the creates idempotent no-ops on existing nodes) and links the value: `{ "nodeId": <dayNodeId> }`. Dates thereby participate in the graph for free: backlinks on a year node list everything dated that year; journals are ordinary trees of day nodes.
- **Precision scoping**: a date property schema declares `datePrecision: "year" | "month" | "day"` (default `"day"`). year-precision links the YEAR node; month links the MONTH node. Values never claim finer granularity than the schema allows.
- **Number formats (display-only, 2026-10-04)**: a number property schema may declare `numberPad` (zero-pad the integer part to N digits — the Pokédex "#0001" case), `numberDecimals` (digits after the point, 0–10), and `numberRounding` (`round` half-away-from-zero — the default when only decimals is set — `floor`, `ceil`, `truncate`). Values stay **exact in the log**; these shape render only, and rendering ignores them for non-number types. `propertySchema.update` keeps absent fields and clears with explicit `null` (the keep-vs-clear contract).
- **Date ranges**: the `date_range` property type (already in the type enum) has value `{ "start": <date-ref|null>, "end": <date-ref|null> }` — either side open. Precision applies to both ends.
- **Link qualifiers (dates for links)**: a node-typed property schema may set `dateQualified: true`; then each value may carry `metadata.startDate` / `metadata.endDate` as **date-node refs through the chain** (PC6, DONE 2026-10-04 as the §34.57 TS reference — the register's schedule-BEFORE-data-accrues ruling; writers ride the `ensureDateChain` pattern, refs stay existence-lenient until the chain exists). **Migration tolerance:** the pre-PC6 ISO-string encoding reads lenient everywhere (panel, export) and **normalizes on write** — the applier rewrites a well-formed `YYYY-MM-DD` string on a dateQualified schema to the deterministic day-node id (the §34.45 bare-uuid precedent; only the two reserved keys, only dateQualified schemas, pure value rewriting — no graph side effects). A qualifier's precision is the ref's chain precision (year/month/day node id). The properties panel renders the small range control next to qualified link chips.
- **Recurrence (compute-on-read — §34.63, owner ruling 2026-10-04 on §34.28 #6):** a date value may carry a recurrence rule in `metadata.repeat` — additive metadata, the startDate/endDate precedent; **no new op, no wire change**. See "Recurrence" below.
- **Picker UX**: one date-selection component with **zoom levels** — a year grid, a month grid, a day grid — switching freely between them; the precision ceiling is the schema's (a year-precision property zooms months/days only to show context, committing at year). Ranges use the picker per end.
- **Storage/convergence**: values are ordinary property JSON; the chain creation rides the op log (client-emitted creates, deterministic ids); edge projection treats date refs like node-typed values (backlinks/journals).
- [x] **Protocol↔query dependency cycle** — DONE 2026-09-27: the zod AST model moved from `packages/query/src/ast.ts` to `packages/protocol/src/query-ast.ts` (the wire-adjacent home — the content grammar's `query` token embeds it, so protocol must not depend on query). `packages/query/src/ast.ts` is now a thin re-export from `@notees/protocol`, so every `import { … } from "@notees/query"` path (apps, compiler/dsl/executor) is unchanged; query runtime-depends on protocol, protocol depends on no workspace package. ## Recurrence — RRULE-lite on date values, compute-on-read (NORMATIVE, §34.63, owner ruling 2026-10-04)

A **recurring event is ONE node**: its date value carries the rule, and the calendar expands **virtual occurrences at read time**. The owner spec ruling (§34.28 #6's compute-on-read option): **no new op type, no wire change, no fixture gate, no client lockstep** — the rule is additive value metadata, exactly like the startDate/endDate qualifiers. Occurrences are **never materialized as nodes** (design law: no hidden objects); editing the event edits the series.

- **Storage**: `metadata.repeat` on the date property value, holding the canonical grammar string. The value's own day IS the series **anchor** — the anchor is never stored inside the rule (one source of truth: the linked day node). Precision coarser than day has no anchor and MUST NOT carry a rule.
- **Grammar** (the stored form, fail-loud parse — `@notees/domain` `parseRecurrenceRule` throws on anything else): `<freq>` or `<freq>/<interval>`; `<freq>` ∈ `daily` | `weekly` | `weekdays` | `monthly` | `yearly`; `<interval>` = integer 2..999 (1 is the default, never written; an explicit `/1` normalizes away). `weekdays` (Mon–Fri) rejects an interval. Clients that don't know the key ignore it — the value stays an ordinary date ref.
- **Expansion semantics** (`occurrenceIsosOf(series, fromIso, toIso, cap?)`, inclusive window): the anchor day is occurrence #0. `daily` = every interval days; `weekly` = every interval weeks on the anchor's weekday; `weekdays` = every Mon–Fri; `monthly` = the anchor's day-of-month every interval months — a month lacking that day (Jan 31 → February) **skips**, RRULE-style; `yearly` = the anchor's month-day every interval years (Feb 29 skips non-leap years, the same rule). Expansion is **capped** (default 366 occurrences): a window wider than the cap **truncates** — callers size the window instead of expecting completeness. A present-but-corrupt rule throws (fail loud — corrupt metadata never reads as "does not repeat").
- **Reads**: calendar surfaces enumerate the workspace's recurring values (a scan of effective date values — occurrences have no materialized hook), then expand per window. The day view's Dated/Tasks sections list a recurring row on every occurrence day with an honest repeats marker (one row per series, never phantom rows); a repeating task schedules on occurrence days and is **never overdue** (missed occurrences roll forward). The month grid dots every occurrence day (anchor-day dots compose with the materialized backlink read).
- **Per-occurrence completion** (§34.69): a recurring TASK's done-toggle in a day context records the occurrence, not the series — `metadata.completedOccurrences` on the recurring date value holds the completed days (local ISO `YYYY-MM-DD` strings, sorted, deduped; absent = none; present-but-corrupt throws, the fail-loud idiom). The toggled occurrence renders done on its day while every other occurrence stays open; reopening removes just that date; the `repeat` rule and any qualifiers ride through untouched. No nodes are materialized — occurrences stay virtual. Writers that don't know the key read an ordinary date value (convergence neutral).
- **Scope limits (documented)**: the shipped picker authors interval-1 rules (the grammar accepts intervals for API/CLI writers). Typed-link target resolution stays the owner-deferred M2 design — a verb MARK on a word has no target; the targeted path a bound verb participates in is a property VALUE over the bound schema (verb = propertySchemaId in the edge index), which surfaces in the target's backlinks named by the schema (§34.69).

- [x] **Plugin manifest grammar** — DONE 2026-10-04 (§34.59): the manifest is DECLARED vocabulary, not an op carrier — registry rows are server state, not log state (the prefs/shares ruling), so there is no envelope, no op type, no fixture gate, and no client lockstep. The normative grammar is the "Plugin manifest grammar" section below; the zod schema (`packages/protocol/src/plugin-manifest.ts`) is its executable form; the server registry (`/api/plugins*`) and the web Plugins tab manage inert rows. The plugin RUNTIME (capability broker, subprocess host, manifest consumption — plan §19 / §34.33 AG7) is explicitly PARKED: `capabilities`, `entrypoint`, and `permissions` are validated and stored, never executed or enforced.

## Plugin manifest grammar (NORMATIVE, §34.59, owner 2026-10-04 — SCHEMA + REGISTRY SHIPPED, RUNTIME PARKED)

A **plugin manifest** is a versioned, strict JSON document a plugin author declares; the host stores and displays it now, and the (parked) runtime will consume it later. `manifestVersion: 1` is the grammar version — additive fields amend the strict schema; a breaking change bumps the literal (a protocol-batch decision). Unknown keys are rejected outright (strict; the no-backward-compatibility owner directive applies).

- **Identity law:** `id` is a lowercase reverse-domain (`com.example.notes`) OR a UUID; `version` is strict semver 2.0.0; the registry keys on the **(id, version)** pair (install is idempotent on it — a repeat install answers the existing row; the same id at a different version is 409, versioned updates ride the runtime). `name`/`description`/`author` are attributes, never identity.
- **`capabilities`** (all optional, all declared-only — declaring grants nothing until the runtime exists): `exportFormats: [{id, label, mime}]` · `importers: [{id, label, mime, mode: "file" | "text"}]` · `commands: [{id, label}]` · `widgets: [{id, label}]` (widgets is the least-designed member — ids/labels only, no renderer contract until the runtime design fixes it). Capability ids are lowercase slugs.
- **`entrypoint`** (reserved): a relative path (no leading slash, no `..` traversal), stored only — NEVER executed by the shipped registry; nothing reads it back into a loader.
- **`permissions`** (reserved): a subset-list over the plugin permission vocabulary — the §26 scope set plus the two plugin-era additions from plan §19 (`events.subscribe` — durable event delivery; `network` — explicit egress, off by default). Validated now; enforcement is entirely runtime-era (a parked runtime enforces nothing).
- **Registry state:** the sync server stores `{manifest JSON, enabled flag, installed_at}` per (id, version) in a `plugin` table on relay.db (server state — the operation log is untouched; verified by test). Management routes `GET/POST /api/plugins`, `DELETE /api/plugins/:id`, `POST /api/plugins/:id/enabled` are owner/admin-scoped (operator key or administrator account; a scoped API key needs the `admin` scope — the first enforcement of that reserved name). The web surface is Workspace Settings → Plugins (list, capability summary, enable toggle, paste-JSON install with client-side validation).

## Templates — `has-template`, instantiation, link-vs-clone (NORMATIVE, §34.25 T1/T2, 2026-10-03)

A **template** is an ordinary node carrying the seeded `template` system class (…0001-000000000013) — fully editable with the real outliner, linkable, taggable, findable in the graph. There is no template node kind (design law). **`has-template`** (fixed UUID `00000000-0000-0000-0000-000000000026`) is the node-typed, `multi: true` property **on class nodes** (`targetClassFilter: ["template"]`, seeded spec): a class's bound templates are the authored values on the class node itself. Owner decisions (§34.25): **D1** relation lives on the class, multi; **D2** template-wins precedence (below); **D3** embeds stay live; **D4** daily-note templates parked.

- **Instantiation = client-side clone composition — no template op type.** The clone engine walks the template subtree depth-first over the store's position-ordered children and composes only existing carriers: one `object.create` per cloned node — fresh UUIDv7 identity per node, `contentAst` copied, `classIds`/`tagIds` seeded on the create — followed by the cloned node's authored `property.set` carriers. Sibling order is reproduced identically on every backend by **anchor chaining**: the first cloned child appends; each following sibling carries `afterId` = the previously cloned sibling's fresh id (`parentId` + the m2 `beforeId`/`afterId` carriers; no fractional-order client logic, identical replay on every replica from the single global log).
- **Instantiate-at-create semantics (create-with-template):** the flow first creates the object (picked class, page placement); the template's root is then **grafted onto the created object** — the object receives the root's `contentAst`, its class assignments minus the `template` marker class, its tags (both re-issued via the OR-Set add carrier), and its **authored** property values; the root's children are cloned beneath the object in order. The template node itself is never referenced by the instance.
- **Link vs clone (A3) — references are links, never duplicated:**
  - `mention`, `class_chip`, `typed_link` tokens keep their target (rename-safe link semantics; Fork 3/Fork 4 unchanged).
  - Tags are **re-issued** on the fresh id (`object.create`'s `tagIds` OR-Set add — add-wins per pair).
  - Class assignments are copied **minus the `template` marker class** (the strip rule: an instance is not a template).
  - Node-typed property values (m2o/m2m `{nodeId}` refs, incl. date-chain refs) copy the reference.
  - `asset_ref` re-points at the **same CAS asset**; `embed_ref` carries the **same live embed** (D3 — never deep-clone the embedded subtree; the embed rule above stands).
  - `whiteboard` layout `cards` geometry is re-keyed to the cloned cards' fresh ids (geometry follows the re-identified children; shapes/strokes are identity-free and copy unchanged). Every other token copies unchanged.
  - Derived class-binding **defaults are never materialized** onto the instance (the derived read model recomputes them from the instance's own classes).
- **D2 — the template wins per property; `defaultValue` fills only what the template leaves unset.** Template-authored values land as authored `property.set` rows on the instance, so the effective read (`authored ?? winning binding defaultValue`) shows template values over binding defaults **by construction**, and every property the template leaves unset stays live to later binding-default edits. Both are per-class configuration; the template instance copies the binding set by copying the class assignments.
